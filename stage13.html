Why this stage exists

GenAI is the single most likely area where an interviewer tests whether you can tell the difference between "I've used ChatGPT" and "I understand how a production LLM system is actually built." Every analytics, product, and consulting role you're targeting now assumes some fluency here — and it's an area where buzzword-level answers get exposed fast (conflating GenAI with traditional ML, believing RAG "eliminates" hallucination, treating "more context" as free). This stage builds real mechanism-level understanding — how attention actually computes a weighted representation, how a RAG pipeline actually retrieves and grounds an answer, how an agent actually decides which tool to call — so you can go two or three questions deep on any of it, while staying scrupulously honest that your personal hands-on work was chatbot product design and rollout, not LLM systems engineering.

03

AI Foundations & ML vs AI vs GenAI

The vocabulary distinction that separates a genuinely fluent answer from a buzzword-salad one.

AI vs. ML vs. GenAI — The Nested Relationship C

Artificial Intelligence is the broadest umbrella: any system performing tasks that normally require human intelligence (including hand-coded rule engines with no learning at all). Machine Learning is the subset that learns patterns from data rather than following hard-coded rules — everything in Stages 6-11 (regression, trees, XGBoost, forecasting) is ML. Generative AI is the subset of ML whose models generate new content (text, images, code) rather than only predicting a label or number — built overwhelmingly on deep learning, most prominently the transformer architecture. Every GenAI model is ML; not every ML model is GenAI; not every AI system is ML at all.

Worked example
-- A single "AI-powered support system" might actually contain all three layers: IF ticket.contains("refund") THEN route_to("billing") -- AI (rule-based), not ML predicted_churn = xgboost_model.predict(customer_features) -- ML (Stage 9), not generative response_draft = llm.generate(ticket_text, context) -- GenAI: generates new text
All three lines could legitimately sit inside one product and all three would honestly be called "AI-powered" — but only the third line is GenAI, and only the second and third are ML. Conflating these in an interview ("we used AI, I mean ML, I mean GenAI, interchangeably") is one of the fastest ways to signal shallow understanding.
Daily-lifeA thermostat with a fixed if-too-cold-turn-on-heat rule is AI (of a sort) but not ML; a thermostat that learns your schedule from behavior is ML; a thermostat that writes you a natural-language explanation of why it adjusted is GenAI.
ConsumerNetflix's recommendation ranking is ML (predicting what you'll rate highly); a chatbot summarizing a show's plot on request is GenAI.
BusinessA churn-prediction model (ML) feeding into an auto-drafted, GenAI-written retention email is a common real pairing — two different technology categories in one workflow.
EnterpriseExactly this layering — XGBoost prediction (Stage 9) plus a GenAI-drafted stakeholder summary — is a realistic evolution of Axtria-style decision-support tooling.
Interview"Is GenAI just ML with more parameters?" — no; scale matters, but the defining difference is generative vs. discriminative modeling (next concept), not size alone.
Your CV"I'd use exactly this AI/ML/GenAI distinction to clarify, precisely, which category the Hero Electronics chatbot's technology actually falls into rather than blurring the three together."

Discriminative vs. Generative Modeling C

A discriminative model learns a decision boundary or a conditional prediction P(y|x) — everything in Stages 6-9 (will this customer churn? what's this call's converted flag?). A generative model learns (or approximates) the underlying data distribution well enough to sample new, plausible data from it — an LLM generating the next token is fundamentally sampling from a learned probability distribution over the entire vocabulary, conditioned on everything so far.

Worked example
-- Discriminative (XGBoost, Stage 9): a fixed input maps to one prediction P(converted=1 | rep_tenure=3, territory="West", call_count=5) = 0.72 -- Generative (LLM): the model outputs a full probability distribution -- over the ENTIRE vocabulary for the next token, then samples from it P(next_token | "The rep's conversion rate was") = {"72%": 0.31, "high": 0.18, "strong": 0.09, "72": 0.07, ...thousands more} sampled -> "72%" (highest-probability token this draw)
The discriminative model outputs one number for one fixed question; the generative model outputs a full probability distribution over ~50,000-100,000+ possible next tokens and samples from it — repeated token-by-token, this sampling process is literally how an LLM "writes" a sentence, which is why the same prompt can produce slightly different phrasing on different runs (unless temperature is set to 0, covered under Prompt Engineering).
Daily-lifeA yes/no weather forecast ("will it rain," discriminative) versus a narrated weather story that could unfold in many equally plausible ways (generative).
ConsumerA spam filter (discriminative: spam or not) versus an email-drafting assistant (generative: produces new text).
BusinessA conversion-probability model (discriminative, Stage 7/9) versus a GenAI-drafted follow-up message to a customer (generative) are complementary, not competing, tools in the same pipeline.
EnterpriseThe natural next evolution of Axtria-style tooling: XGBoost predicts which reps/territories need attention (discriminative), a GenAI layer drafts the stakeholder-facing explanation (generative).
Interview"Can a generative model do discrimination/classification?" — yes, by construction: you can prompt an LLM to output only "yes" or "no," effectively using a generative model discriminatively, though a purpose-built discriminative model is usually cheaper and more reliable for a fixed classification task.
Your CV"This distinction is exactly what I'd use to explain why XGBoost (Stage 9) and an LLM chatbot are fundamentally different technology categories solving different problem shapes, not competing options for the same task."
04

LLM Fundamentals & Transformers

The architecture underneath every modern LLM — self-attention and the token-by-token generation loop.

The Transformer & Self-Attention C

The transformer architecture (2017, "Attention Is All You Need") processes an entire sequence in parallel rather than word-by-word like older RNNs, using self-attention: for every token, the model computes how much every other token in the sequence should "attend to" it, producing a context-aware representation. Each token is projected into a Query, Key, and Value vector; attention weights come from the scaled dot-product of Queries and Keys, then those weights are used to combine the Values into a new, context-enriched representation for each token.

Worked example — toy 3-token attention
-- Sentence: "rep hit target" — simplified to 2D query/key vectors for illustration Q(target) = [1.0, 0.5] K(rep) = [0.9, 0.1] K(hit) = [0.2, 0.8] K(target) = [1.0, 0.5] -- raw scores = dot product Q . K score(rep) = 1.0*0.9 + 0.5*0.1 = 0.95 score(hit) = 1.0*0.2 + 0.5*0.8 = 0.60 score(target) = 1.0*1.0 + 0.5*0.5 = 1.25 -- softmax to get attention weights (normalized, sums to 1) softmax([0.95, 0.60, 1.25]) ≈ [0.36, 0.25, 0.39]
The word "target" ends up attending most to itself (0.39) and almost as much to "rep" (0.36) — meaning its final context-aware representation is a weighted blend that's ~39% its own value, ~36% "rep"'s value, and ~25% "hit"'s value, letting the model encode "whose target this is" directly into the token's representation. Stacking many of these attention layers (with multiple parallel "heads" looking at different relationship types) is what lets a transformer build up rich, long-range contextual understanding across a whole document.
Daily-lifeReading a sentence and automatically knowing which earlier word a pronoun refers to ("the rep called the client because she was worried") — your brain is doing an attention-like weighting across the sentence.
ConsumerWhy ChatGPT can correctly answer a question referencing something you said several messages ago — long-range attention across the conversation context.
BusinessWhy an LLM summarizing a long stakeholder email thread correctly attributes each commitment to the right person, even across many paragraphs.
EnterpriseThe mechanism-level reason a modern GenAI layer could, in principle, read a long Axtria-style stakeholder report and correctly track which numbers belong to which territory across pages of text.
Interview"Why not just use the older RNN/LSTM architecture?" — RNNs process sequentially (word by word), which is slow to train and struggles with long-range dependencies; transformers process the whole sequence in parallel and use attention to directly connect distant tokens, which is both faster to train and better at long context.
Your CV"I wouldn't claim to have implemented attention from scratch, but I can explain, at this level of mechanism, why an LLM 'understands' context the way it does — which is exactly the kind of technical grounding a GenAI product conversation needs."

Tokenization & the Autoregressive Generation Loop C

Text is broken into tokens (subword units, via algorithms like Byte-Pair Encoding — not always whole words) before the model ever sees it; a rough rule of thumb is ~4 characters or ~0.75 words per token in English. Autoregressive generation means the model predicts one token at a time, each new token conditioned on everything generated so far, feeding its own output back in as input for the next step — this is why LLMs "write" left to right and why generation is inherently sequential (and thus slower/costlier) even though understanding the input can be parallelized.

Worked example — token counting & cost
-- "The rep's conversion rate improved by twelve percent this quarter." -- ~13 words -> roughly 17 tokens (some words split: "twelve" + "percent" fine, -- but a rarer word like "Databricks" might split into "Data" + "bricks") tokens_in_prompt = 450 -- a moderate system+context prompt tokens_generated = 180 -- the model's response price_per_1k_input = $0.003 price_per_1k_output = $0.015 cost = (450/1000)*0.003 + (180/1000)*0.015 = 0.00135 + 0.0027 = $0.00405 per request
A single chatbot exchange like this costs just under half a cent — trivial at low volume, but at Hero-Electronics-chatbot scale (say 50,000 queries/month, similar order of magnitude to the real query coverage the CV cites), that's roughly $200/month in raw model cost alone, before infrastructure, before the "% of queries an LLM even needs to touch" question — exactly the kind of unit-economics reasoning covered under AI Economics later in this stage.
Daily-lifeSounding out an unfamiliar word syllable-by-syllable rather than recognizing it whole is roughly analogous to a rare word being split into subword tokens.
ConsumerWhy ChatGPT's response streams in visibly word-by-word rather than appearing all at once — it's literally generating (and often streaming) one token at a time.
BusinessWhy a longer, more elaborate system prompt directly increases per-request cost — every extra token in the prompt is billed, every time, on every request.
EnterpriseThe direct unit-economics lens an Axtria- or Hero-Electronics-scale chatbot rollout needs before committing to an LLM-based architecture over a cheaper rule-based one.
Interview"Why is LLM output generation slower than reading the prompt?" — reading (encoding) the prompt is parallelizable across all tokens at once; generating output is inherently sequential, one token conditioned on the last, which is the real bottleneck in LLM latency.
Your CV"If asked to scope a GenAI-based version of the chatbot, I'd start with exactly this token-cost math to compare it honestly against the rule-based approach the original rollout likely used."

Prompt Engineering

The cheapest, fastest lever for controlling LLM behavior — and the first thing to try before RAG or fine-tuning.

Prompting Techniques — Zero-Shot, Few-Shot & Chain-of-Thought B

Zero-shot gives only an instruction, no examples. Few-shot includes a handful of worked input-output examples in the prompt itself, letting the model infer the pattern/format without any weight updates. Chain-of-thought (CoT) prompting asks the model to reason step-by-step before answering, which measurably improves accuracy on multi-step reasoning tasks by giving the model "room" to work through intermediate steps rather than jumping straight to a final token.

Worked example
-- Zero-shot (often inconsistent formatting): "Classify this support ticket's urgency." -- Few-shot (shows the model the exact desired format): "Classify urgency as Low/Medium/High. Ex: 'app is slow sometimes' -> Low Ex: 'payment failed, customer charged twice' -> High Now classify: 'cannot reset password'" -> Medium (consistent with the demonstrated format, no explanation needed) -- Chain-of-thought (for a harder, multi-step business question): "A rep's conversion rate is 18%. If call volume rises from 200 to 260 calls/month with the same rate, how many more conversions per month? Think step by step." -> Step 1: 200*0.18=36 conversions now. Step 2: 260*0.18=46.8≈47. Step 3: 47-36=11 more conversions/month.
Few-shot examples eliminate the ambiguity zero-shot leaves about output format (Low/Medium/High vs. a full sentence), while chain-of-thought on the arithmetic question forces the model to compute 200×0.18 and 260×0.18 as explicit intermediate steps rather than guessing a plausible-sounding final number directly — this is the single most reliable prompting technique for reducing arithmetic and multi-step reasoning errors.
Daily-lifeShowing someone two solved examples of a puzzle type before asking them to solve a third (few-shot) versus just describing the rules abstractly (zero-shot).
ConsumerA customer-support chatbot given 3-5 example resolved tickets in its prompt to match your company's exact tone and format.
BusinessAsking an LLM to "show your work" on a business-case-style calculation (CoT) measurably reduces silent arithmetic mistakes in the final answer.
EnterpriseDirectly the technique to try first — before building any RAG or fine-tuning infrastructure — when scoping a GenAI feature for a Hero-Electronics-style chatbot rollout.
Interview"When would few-shot NOT help?" — when the task needs genuinely new knowledge the model doesn't have (a private policy document), not just a formatting/style pattern — that's a RAG problem, not a prompting problem.
Your CV"This exact zero-shot-vs-few-shot-vs-CoT toolkit is what I'd reach for first if scoping any GenAI feature for a product like the Hero Electronics chatbot before considering heavier infrastructure."

Prompt Structure, Roles & Sampling Parameters B

Modern LLM APIs structure a conversation into roles: a system message (persistent instructions/persona), user messages (the actual query), and assistant messages (the model's prior responses, for multi-turn context). Generation is also controlled by sampling parameters: temperature (0 = deterministic/greedy, higher = more random/creative sampling from the probability distribution), top-p (nucleus sampling — only sample from the smallest set of tokens whose cumulative probability exceeds p), and max tokens (a hard output-length cap).

Worked example
system: "You are a support assistant for a telecom hardware company. Be concise. Never make up policy details you're not given." user: "Can I return a router after 45 days?" -- temperature=0.0 -> deterministic, best for factual/policy answers -- temperature=0.9 -> more varied phrasing, better for creative drafting, -- WRONG choice for a policy-answering bot (invites inconsistent answers)
A support bot answering policy questions should almost always run at temperature=0 (or very close to it) — every user asking the same question should get the same, consistent, factual answer; a marketing-copy generation task is exactly the opposite case, where a higher temperature intentionally introduces useful variety. Choosing the wrong temperature for the task is a common, easily-avoidable production mistake.
Daily-lifeA strict, always-the-same-answer reference desk (temperature≈0) versus a brainstorming partner who intentionally offers different angles each time (higher temperature).
ConsumerWhy the same question to a customer-service bot should get a consistent policy answer every time, not a different, possibly-contradictory one on each retry.
BusinessA marketing-copy generation tool intentionally runs hotter (higher temperature) than a compliance-answer bot — the "right" temperature is task-dependent, not a universal default.
EnterprisePrecisely the kind of production configuration decision that separates a carefully-scoped GenAI feature from a naive one, for a chatbot handling real customer queries at Hero-Electronics scale.
Interview"What's the difference between temperature and top-p?" — temperature reshapes the whole probability distribution's sharpness; top-p truncates the sampling pool to the smallest set of tokens covering probability mass p, then samples within it — they're often used together, not as alternatives.
Your CV"If I were formalizing a GenAI version of the Hero Electronics chatbot, defining the system prompt and locking temperature near 0 for policy-sensitive answers is exactly the first production decision I'd make."

Embeddings & Vector Search

How unstructured text becomes something you can mathematically compare — the foundation RAG is built on.

What Embeddings Are & Cosine Similarity C

An embedding is a dense numeric vector (typically hundreds to low thousands of dimensions) representing a piece of text such that semantically similar text ends up with similar vectors — produced by a separate embedding model, distinct from the generative LLM itself. Cosine similarity measures the angle between two vectors (ignoring magnitude), the standard way to compare "how semantically close" two embeddings are, ranging from -1 (opposite) to 1 (identical direction).

Worked example — toy 2D embeddings
embed("rep missed quota") = [0.8, 0.6] embed("rep underperformed") = [0.75, 0.66] embed("weather forecast") = [-0.2, 0.9] -- cosine_similarity(A,B) = (A·B) / (||A|| * ||B||) A·B = 0.8*0.75 + 0.6*0.66 = 0.6 + 0.396 = 0.996 ||A|| = sqrt(0.8²+0.6²) = 1.0 ||B|| = sqrt(0.75²+0.66²) ≈ 0.9997 cos_sim = 0.996 / (1.0 * 0.9997) ≈ 0.996 -- vs. the unrelated sentence: A·C = 0.8*-0.2 + 0.6*0.9 = -0.16+0.54 = 0.38 ||C|| = sqrt(0.2²+0.9²) ≈ 0.922 cos_sim(A,C) = 0.38/(1.0*0.922) ≈ 0.412
"rep missed quota" and "rep underperformed" score a cosine similarity of ~0.996 (nearly identical direction — correctly recognized as semantically close despite sharing almost no exact words), while the unrelated "weather forecast" sentence scores only ~0.412 — this numeric gap is exactly what a vector search system uses to retrieve the right document even when the query and the source text don't share vocabulary.
Daily-lifeA librarian who understands that "how to fix a leaky faucet" and "plumbing repair guide" mean the same thing, even with zero shared words — embeddings capture that same kind of meaning-based closeness numerically.
ConsumerA product search that returns "running shoes" results for the query "sneakers for jogging" — semantic, not just keyword, matching.
BusinessClustering thousands of open-ended customer feedback comments by semantic similarity rather than exact keyword matching to find real themes.
EnterpriseHow a GenAI-based version of the Hero Electronics chatbot could match a customer's oddly-phrased query ("thing won't turn on") to the right knowledge-base article even without exact keyword overlap.
Interview"Why cosine similarity instead of Euclidean distance for embeddings?" — cosine similarity ignores vector magnitude and focuses purely on direction (meaning), which is usually what you want for text; magnitude differences in embeddings often just reflect text length, not meaning.
Your CV"This is the mechanism I'd point to if asked how a smarter version of the chatbot could match a customer's own words to the right knowledge base entry, rather than requiring exact keyword rules."

Vector Databases & Approximate Nearest Neighbor Search C

A vector database (Pinecone, Weaviate, pgvector, Milvus, FAISS) stores embeddings and supports fast similarity search over them. Exact nearest-neighbor search is O(n) per query — comparing against every stored vector — which doesn't scale to millions of documents; production systems use Approximate Nearest Neighbor (ANN) algorithms (like HNSW — Hierarchical Navigable Small World graphs) that trade a small amount of accuracy for dramatically faster lookup.

Worked example — why ANN matters at scale
-- Exact brute-force search over N documents, each a D-dim vector: N = 5,000,000 documents D = 1536 dimensions (typical embedding size) comparisons_per_query = N = 5,000,000 -- at ~1 microsecond per comparison (optimistic): time_per_query ≈ 5,000,000 * 1e-6 sec = 5.0 seconds -- too slow for a live chatbot -- HNSW-style ANN: effectively O(log N) graph traversal comparisons_per_query ≈ log2(5,000,000) * constant ≈ 23 * small_constant time_per_query ≈ tens of milliseconds -- production-viable
Brute-force exact search over 5 million documents is roughly 5 full seconds per query — completely unusable for a live chatbot response; an HNSW-style ANN index turns that into tens of milliseconds by never comparing against every vector, only a smart, graph-navigated subset — at the honest cost of occasionally missing the single truly-closest match in exchange for near-real-time latency, a tradeoff every production RAG system accepts deliberately.
Daily-lifeFinding a specific book by wandering a library's well-organized subject-sorted aisles (ANN, fast, occasionally not the single perfect match) versus reading the spine of literally every book in the building (exact search, guaranteed correct, impossibly slow).
ConsumerWhy a "similar products" recommendation on an e-commerce site returns instantly even across a catalog of millions of items.
BusinessChoosing a vector database (managed like Pinecone vs. self-hosted like pgvector/FAISS) is a real infrastructure/cost decision, not just a technical footnote, when scoping any RAG-based product.
EnterpriseThe infrastructure layer a genuinely production-grade, knowledge-base-grounded version of the Hero Electronics chatbot would need if the knowledge base grew beyond a small, hand-curated FAQ set.
Interview"What's the tradeoff ANN makes?" — a small, usually acceptable loss of retrieval accuracy (it might return the 2nd-closest match instead of the 1st) in exchange for orders-of-magnitude faster query time at scale — essential once a knowledge base exceeds roughly tens of thousands of documents.
Your CV"I'd flag this exact scaling tradeoff if asked how a chatbot's knowledge base could grow from a small FAQ to a large document set without breaking response-time expectations."

RAG — Retrieval-Augmented Generation

Grounding an LLM's answers in real, retrievable documents instead of relying solely on what it memorized during training.

The RAG Pipeline, End to End C

RAG combines retrieval (finding relevant source documents via embedding similarity) with generation (an LLM writing an answer grounded in those retrieved documents), rather than relying purely on the LLM's frozen training-time knowledge. The pipeline: (1) chunk and embed a document corpus offline, storing vectors in a vector database; (2) at query time, embed the user's question; (3) retrieve the top-k most similar chunks; (4) inject those chunks into the LLM's prompt as context; (5) the LLM generates an answer grounded in that retrieved context, ideally citing it.

Worked example
user_query = "Can a router be returned after 45 days?" -- Step 1-3: embed query, retrieve top-2 chunks by cosine similarity retrieved = [ "Return Policy §4.2: Hardware returns accepted within 30 days of purchase...", "Extended warranty claims (separate from returns) accepted within 12 months..." ] -- Step 4: build the augmented prompt prompt = system("Answer ONLY using the provided context. If not covered, say so.") + context(retrieved) + user_query -- Step 5: grounded generation -> "Based on the return policy provided, hardware returns are accepted within 30 days of purchase — a 45-day-old router would not qualify for a standard return, though it may be eligible under the separate 12-month warranty process. [Source: Return Policy §4.2]"
The LLM never "knew" the 30-day policy from training — it correctly answered "no, but here's the alternative" only because the retrieval step surfaced the exact right policy chunk and the prompt explicitly instructed the model to answer only from that provided context, which is what makes the answer both accurate and honestly sourced rather than a plausible-sounding guess.
Daily-lifeA well-prepared expert witness who looks up the exact regulation before answering, rather than answering purely from memory — RAG is the LLM equivalent of "look it up first."
ConsumerA shopping assistant chatbot correctly citing your specific order's actual return window instead of a generic, possibly-wrong memorized policy.
BusinessAn internal HR chatbot answering from the actual, current employee handbook rather than a stale, generic answer the model happened to memorize during training.
EnterprisePrecisely the architecture the honest Level C framing above points to as the plausible next evolution of the Hero Electronics chatbot — grounding its 80%-coverage answers in an actual, retrievable knowledge base rather than either hard-coded rules or an ungrounded LLM.
Interview"Why not just fine-tune the model on the policy documents instead?" — fine-tuning bakes knowledge into weights (expensive to update, no easy "as of" freshness, and models still hallucinate specifics); RAG keeps the source of truth in an easily-updatable document store and lets the LLM cite it — see the Fine-Tuning section's decision framework.
Your CV"This end-to-end RAG pipeline is exactly what I'd propose as the concrete next step if asked how to make the chatbot's 20% unhandled-query gap smaller without hard-coding more rules by hand."

Chunking Strategy & Retrieval Quality C

How a document is split into chunks before embedding directly determines retrieval quality: chunks too large dilute the embedding's specificity (burying the relevant sentence among irrelevant ones) and waste context budget; chunks too small lose surrounding context needed to make sense of the retrieved snippet. Common strategies: fixed-size with overlap, semantic/paragraph-based splitting, and hierarchical chunking. Reranking (a second, more precise pass over the initial top-k retrieved candidates, often with a cross-encoder model) further improves precision before the final context is assembled.

Worked example
-- Too large: one 2,000-word chunk covering the ENTIRE return/warranty/shipping -- policy dilutes the embedding -- it's now "about everything," not specifically -- about the 30-day return window, so it may not rank in the top-k at all -- Better: chunk by section, ~150-300 words with slight overlap chunk_1 = "§4.1 Shipping ... [context] ..." chunk_2 = "§4.2 Returns: Hardware returns accepted within 30 days... [context]" chunk_3 = "§4.3 Warranty: Extended warranty claims accepted within 12 months..." -- Retrieval on "return after 45 days" now correctly ranks chunk_2 highest -- because its embedding is specifically, tightly about returns
Splitting the monolithic policy document into section-sized chunks turns a diluted, everything-and-nothing embedding into three sharply distinct ones — the return-specific chunk now dominates retrieval for a return-specific query, which is the single highest-leverage lever for improving a RAG system's answer quality, often more impactful than which embedding model or LLM you choose.
Daily-lifeAn index card with one clear fact is easier to find in a filing box than a whole binder you'd have to flip through — chunk size is choosing the right card size.
ConsumerWhy a well-built AI shopping assistant answers a specific spec question precisely instead of dumping the entire product manual at you.
BusinessThe unglamorous but highest-ROI engineering work on most real RAG projects is chunking strategy and retrieval tuning, not swapping which LLM generates the final answer.
EnterpriseExactly the kind of practical, iterative tuning work a RAG-based knowledge-grounded chatbot for Hero Electronics-style support would need — right-sizing chunks around natural policy sections, not arbitrary character counts.
Interview"How would you debug a RAG system giving wrong answers?" — first check retrieval (is the RIGHT chunk even being retrieved? often it's a chunking/embedding problem, not a generation problem), then check whether the prompt properly constrains the model to only use retrieved context, only then suspect the generation model itself.
Your CV"If a GenAI chatbot gave a wrong policy answer, this retrieval-first debugging instinct — check what was actually retrieved before blaming the model — is exactly the diagnostic approach I'd take."

Agents

LLMs that don't just answer — they decide, act, observe, and iterate.

The Agent Loop — ReAct & Tool Use C

An agent is an LLM given access to tools (functions it can call — a database query, a web search, a calculator, an internal API) and looped so it can reason about which tool to call, observe the result, and decide the next step, rather than answering in one shot. The ReAct pattern (Reason + Act) makes this explicit: the model alternates between a Thought (reasoning about what to do next), an Action (a tool call), and an Observation (the tool's result), repeating until it has enough information to give a final answer.

Worked example — ReAct trace
user: "Is rep #4471's conversion rate above the West region average this quarter?" Thought: I need rep #4471's conversion rate AND the West region average. Neither is in my training data -- I need to query the database. Action: query_db("SELECT conversion_rate FROM reps WHERE rep_id=4471") Observation: 0.24 Thought: Now I need the West region's average conversion rate. Action: query_db("SELECT AVG(conversion_rate) FROM reps WHERE region='West'") Observation: 0.19 Thought: 0.24 > 0.19, so yes, rep #4471 is above the regional average. Final Answer: "Yes — rep #4471's conversion rate (24%) is above the West region average (19%) this quarter."
The agent correctly recognized it couldn't answer from memory alone, made two separate, well-scoped tool calls to get real, current numbers, and only then composed a final answer — this tool-grounded loop is what separates an "agent" from a plain LLM call, and is exactly what prevents the model from confidently hallucinating a plausible-sounding but fabricated conversion rate.
Daily-lifeA capable assistant who says "let me check the calendar" and actually looks, rather than guessing whether you're free Thursday — checking a real source before answering.
ConsumerA travel-booking assistant that actually calls a real flight-search API rather than inventing plausible-sounding flight times and prices.
BusinessAn analytics-copilot agent that writes and runs a real SQL query against your warehouse rather than guessing what a metric's value probably is.
EnterpriseA realistic next-generation version of a Hero-Electronics-style support bot: instead of a fixed rule tree, an agent that can actually query order status or warranty records via a tool call before answering.
Interview"What's the biggest risk with agents?" — an agent can take real, consequential actions (not just generate text), so ungrounded reasoning, tool-call errors, or a poorly-scoped tool (e.g., one that can delete data) carry real operational risk — guardrails and scoped permissions matter far more than for a plain chat LLM.
Your CV"This tool-use pattern is the honest answer to 'could the chatbot actually look things up instead of just answering from a script' — it's the real mechanism, even though I haven't personally built an agent in production."

Multi-Agent Orchestration Patterns C

Complex tasks are sometimes split across multiple specialized agents rather than one generalist agent: a common pattern is an orchestrator/planner agent that decomposes a task and delegates subtasks to specialist agents (a retrieval agent, a code-execution agent, a summarization agent), then synthesizes their outputs. Frameworks like LangChain, LlamaIndex, and CrewAI provide scaffolding for this, though the core pattern — decompose, delegate, synthesize, with clear handoff contracts between agents — is framework-agnostic.

Worked example
user: "Prepare a one-page brief on West region performance this quarter, with a chart and three recommended actions." Orchestrator decomposes into 3 subtasks: -> Data Agent: query_db(...) -> returns structured metrics -> Viz Agent: generate_chart(metrics) -> returns chart image -> Writing Agent: draft_brief(metrics, chart, tone="executive") -> returns final one-pager Orchestrator synthesizes: assembles the three outputs into one document, checks consistency (does the written brief's numbers match the chart?), returns final result to the user.
Splitting the task across specialist agents lets each one use a narrower, more reliable toolset (the Data Agent only ever queries the database; the Writing Agent never touches raw SQL) — the orchestrator's consistency check (do the numbers in the prose match the chart?) is a deliberate safeguard against exactly the kind of silent, hard-to-catch inconsistency that a single do-everything agent is more prone to.
Daily-lifeA project manager (orchestrator) breaking a task into pieces for a researcher, a designer, and a writer (specialists), then reviewing their combined output before it goes out.
ConsumerA trip-planning app that internally coordinates a flights agent, a hotels agent, and an itinerary-writing agent behind one simple user-facing chat interface.
BusinessA GenAI analytics copilot that separates "query the data" from "write the narrative" into different agents, so a data error doesn't get silently laundered into confident-sounding prose.
EnterpriseDirectly the architecture behind an "agentic analytics workflow" style GenAI portfolio project — data retrieval, visualization, and executive-summary writing as separable, auditable agent stages.
Interview"When is a single agent better than multiple?" — for genuinely simple, single-tool tasks, orchestration overhead (extra latency, more failure points, more cost from multiple LLM calls) isn't worth it; multi-agent patterns earn their complexity on tasks that are actually decomposable into distinct, specializable subtasks.
Your CV"I'd describe this orchestrator/specialist pattern as the honest, correct-scale answer if asked how a GenAI system could go beyond a single chatbot into a fuller decision-support workflow — without overclaiming I've built one myself."

Fine-Tuning

When (and when not) to actually change a model's weights, rather than just prompting or retrieving.

Fine-Tuning vs. RAG vs. Prompt Engineering — The Decision Framework B

The three levers solve different problems and should be tried in roughly this order: prompt engineering first (cheap, instant, good for format/style/reasoning-process control); RAG next (when the model needs access to specific, current, or private knowledge it wasn't trained on); fine-tuning last (when you need to change the model's underlying behavior, tone, or task-specific skill in a way prompting/RAG can't reach — expensive, slower to iterate, and doesn't solve a knowledge-freshness problem the way RAG does).

Worked example — decision walkthrough
Problem A: "The bot's answers are too formal, we want a warmer tone." -> Prompt engineering (system prompt tone instruction). Cheapest, fastest. Problem B: "The bot needs to answer questions about OUR specific, frequently-updated product catalog and return policy." -> RAG. The knowledge is specific, private, and changes often -- baking it into weights via fine-tuning would go stale immediately. Problem C: "The bot needs to consistently follow our exact internal ticket-classification taxonomy across thousands of edge cases, in a very specific structured output format, better than prompting alone reliably achieves." -> Fine-tuning. This is a durable BEHAVIOR/skill change, not a knowledge-lookup problem -- a good candidate for supervised fine-tuning on labeled examples.
Misapplying the wrong lever is a common, expensive mistake: fine-tuning Problem B's catalog knowledge into the model would require expensive re-training every time the catalog changes and still wouldn't guarantee accurate recall of specific facts; prompting alone for Problem C would likely stay inconsistent across thousands of edge cases in a way fine-tuning on real labeled examples reliably fixes.
Daily-lifeGiving someone a cheat-sheet to reference (RAG) is faster than sending them back to school to relearn a skill (fine-tuning) — use the cheaper option unless the deeper one is truly needed.
ConsumerWhy a shopping assistant's product-catalog knowledge is virtually always RAG-based (catalogs change constantly) rather than fine-tuned into the model.
BusinessA support-ticket auto-classifier that needs to hit a very specific, nuanced internal taxonomy reliably is a much stronger fine-tuning candidate than a general Q&A bot.
EnterpriseThe exact triage a Hero-Electronics-style chatbot rollout should walk through before committing engineering budget: is this a tone problem, a knowledge problem, or a behavior problem — each has a different, correctly-scoped fix.
Interview"Would you ever combine RAG and fine-tuning?" — yes, commonly: fine-tune a model to better follow your desired output format/behavior, while still using RAG to supply current, specific facts — they're complementary levers, not mutually exclusive.
Your CV"This decision framework is exactly the reasoning I'd walk an interviewer through if asked how I'd evolve the chatbot's underlying technology rather than jumping straight to 'we'd fine-tune a model.'"

Fine-Tuning Methods — Full Fine-Tuning, LoRA/PEFT & RLHF C

Full fine-tuning updates every model weight — most accurate but extremely expensive in compute/memory, often impractical for large models. Parameter-Efficient Fine-Tuning (PEFT) methods like LoRA (Low-Rank Adaptation) freeze the original weights and train only small, added low-rank matrices, capturing most of the benefit at a fraction of the cost. RLHF (Reinforcement Learning from Human Feedback) is a distinct further step — used by model providers to align a base model's behavior with human preferences (helpfulness, safety) using human-ranked comparisons, not typically something an individual team does themselves.

Worked example — LoRA's parameter-efficiency math
-- A single weight matrix in a mid-size LLM layer: original_matrix = 4096 x 4096 = 16,777,216 trainable parameters (full fine-tune) -- LoRA: freeze the original, add two small low-rank matrices instead -- rank r=8 (a common choice) matrix_A = 4096 x 8 = 32,768 params matrix_B = 8 x 4096 = 32,768 params lora_params = 32,768 + 32,768 = 65,536 trainable parameters reduction = 65,536 / 16,777,216 = 0.0039 -> ~0.4% of the original parameter count
LoRA trains roughly 0.4% as many parameters as full fine-tuning for this single layer (and the effect compounds across a whole model with many such layers) — this dramatic reduction is why LoRA-style fine-tuning is feasible on modest hardware and in reasonable time, versus full fine-tuning of a large model requiring substantial multi-GPU infrastructure most individual teams don't have.
Daily-lifeAdding a small, targeted addendum to an existing detailed contract (LoRA — cheap, additive, reversible) versus rewriting the entire contract from scratch (full fine-tuning).
ConsumerWhy many "custom AI personas" or specialized assistants you see from smaller companies are LoRA-tuned on top of a large base model rather than trained from scratch.
BusinessLoRA fine-tuning is realistically within reach for a mid-size company's budget/timeline; full fine-tuning of a frontier-scale model generally isn't, without major infrastructure investment.
EnterpriseIf a company genuinely needed to fine-tune a support-classification model, LoRA/PEFT is the realistic, budget-appropriate path — not full fine-tuning, and definitely not RLHF, which is a base-model-provider-level undertaking.
Interview"What does RLHF actually change that supervised fine-tuning doesn't?" — supervised fine-tuning teaches the model to imitate labeled examples; RLHF further optimizes the model against a learned reward signal built from human preference rankings, which is how base models are aligned to be helpful/harmless rather than just imitative.
Your CV"I'd be honest that I haven't personally run a fine-tuning job, but I can explain precisely why LoRA — not full fine-tuning, not RLHF — is the realistic method if a team like Hero Electronics' technical team ever needed to go that route."

AI Evaluation & Hallucination

How you actually know whether a GenAI system is working — and the failure mode every stakeholder worries about first.

LLM Evaluation — Metrics & Methods C

Evaluating generated text is harder than evaluating a classifier's accuracy because there's often no single "correct" output. Automated metrics like ROUGE (overlap-based, common for summarization) and BLEU (precision-based n-gram overlap, common for translation) give a rough proxy but miss semantic correctness. LLM-as-judge (using a strong LLM to score another model's outputs against a rubric) has become a common, more semantically-aware evaluation method, alongside human evaluation (the gold standard, but slow/expensive) and task-specific automated checks (does the output parse as valid JSON? does a generated SQL query actually run?).

Worked example — toy ROUGE-1 calculation
reference = "the rep exceeded quota this quarter" generated = "rep beat quota this quarter" -- ROUGE-1 = unigram overlap between generated and reference ref_words = {the, rep, exceeded, quota, this, quarter} (6 unique) gen_words = {rep, beat, quota, this, quarter} (5 unique) overlap = {rep, quota, this, quarter} = 4 words recall = overlap / len(ref_words) = 4/6 = 0.667 precision = overlap / len(gen_words) = 4/5 = 0.80 F1 = 2*(precision*recall)/(precision+recall) = 2*(0.8*0.667)/(0.8+0.667) = 1.067/1.467 ≈ 0.727
ROUGE-1 F1 ≈ 0.73 for two sentences that are semantically nearly identical ("exceeded" vs. "beat" are synonyms ROUGE can't detect) — this is exactly ROUGE's known weakness: it measures surface word overlap, not meaning, which is why LLM-as-judge or human evaluation is often layered on top for anything where semantic correctness (not just word overlap) is what actually matters.
Daily-lifeA teacher grading an essay purely by counting matched keywords (ROUGE-like) versus actually reading it for understanding (LLM-as-judge/human eval) — the first is fast but misses paraphrased correct answers.
ConsumerWhy a translation app's internal quality scores don't always match how natural a translation actually reads to a native speaker.
BusinessBefore shipping any GenAI feature, defining what "good" even means (task-specific checks, LLM-as-judge rubric, or human review) is a prerequisite, not an afterthought.
EnterpriseExactly the evaluation rigor a GenAI-based chatbot upgrade at Hero Electronics would need before replacing rule-based logic that had a known, measured 80% coverage rate — you can't claim improvement without a real evaluation methodology.
Interview"Why not just use accuracy like a classifier?" — most GenAI outputs are open-ended text with many valid phrasings, so there's rarely one "correct" string to match exactly against — evaluation has to account for semantic equivalence, which simple exact-match accuracy cannot.
Your CV"I'd insist on defining evaluation criteria upfront for any GenAI chatbot upgrade — exactly the kind of rigor that distinguishes a real engineering process from just 'it feels better.'"

Hallucination — Detection & Mitigation B

Hallucination is an LLM generating fluent, confident-sounding text that is factually wrong or unsupported — a fundamental consequence of how generative models work (sampling plausible next tokens, not looking anything up, unless explicitly grounded via RAG). Mitigation strategies: RAG grounding with explicit "answer only from provided context" instructions, requiring citations, lower temperature for factual tasks, a fact-checking/verification pass (sometimes another LLM call), and — critically — designing the product to let the model say "I don't know" rather than always producing an answer.

Worked example
user: "What's our return policy for a product bought 200 days ago?" -- WITHOUT grounding/instruction: model may hallucinate a plausible-sounding -- but fabricated answer, because it was never told it's allowed to say "unsure" -> "Our extended policy allows returns up to 365 days for store credit." (fabricated -- no such policy chunk was ever retrieved) -- WITH RAG grounding + explicit "say so if not covered" instruction: retrieved = ["Return Policy §4.2: 30-day return window from purchase date."] -> "Based on the return policy provided, returns are accepted within 30 days of purchase -- a product bought 200 days ago would not be eligible for a standard return. I don't have information on any extended/store-credit policy beyond that -- please check with support directly."
The ungrounded version fabricated a specific, plausible-sounding "365 days for store credit" policy that doesn't exist anywhere in the source material — exactly the kind of confidently-wrong answer that erodes user trust fastest; the grounded version correctly refuses to speculate beyond what was actually retrieved, which is the single most important behavior to explicitly design for in any customer-facing GenAI product.
Daily-lifeA confident coworker who guesses an answer rather than saying "I'm not sure, let me check" — fluent but unreliable, exactly the hallucination failure mode.
ConsumerA well-publicized real-world failure mode: chatbots confidently citing fake policies, fake case law, or fake product specs that sound entirely plausible.
BusinessThe single biggest stakeholder trust risk in any GenAI rollout — one confidently-wrong customer-facing answer can do more reputational damage than the entire feature's upside.
EnterpriseThe exact risk a Hero-Electronics-style GenAI chatbot upgrade would need explicit safeguards against — the current rule-based system's 80% coverage is at least predictable; an ungrounded LLM replacing it without hallucination safeguards could be worse, not better, on trust.
Interview"Does RAG eliminate hallucination?" — no, it substantially reduces it by grounding answers in real retrieved text, but doesn't eliminate it (the model can still misread or misstate the retrieved context, or hallucinate when retrieval fails to find anything relevant) — a Red Flag worth naming explicitly.
Your CV"Designing the bot to say 'I don't know, let me connect you with support' instead of guessing is exactly the kind of product judgment call I'd bring from having owned the original chatbot's scoping decisions."

AI Product Development & Economics

Building a GenAI feature is a product discipline, not just a model-selection decision — and it has real, computable unit economics.

AI Product Development Lifecycle & Eval-Driven Development B

A disciplined GenAI product process: (1) define the problem and success criteria before touching a model, (2) build a small evaluation set (representative real examples with known-good answers) before building the feature, (3) prototype with prompting first, (4) measure against the eval set, (5) only escalate to RAG/fine-tuning if prompting doesn't meet the bar, (6) ship with monitoring, human-in-the-loop fallback, and a feedback loop for continued improvement — "eval-driven development" mirrors test-driven development, but for probabilistic, non-deterministic systems.

Worked example
Step 1: Success criteria -- "95%+ of policy questions answered correctly, zero fabricated policy details, escalate to human when unsure" Step 2: Eval set -- 50 real historical customer questions + correct answers, curated from the existing chatbot's actual query logs Step 3: Prototype -- zero-shot prompted LLM, no RAG yet Step 4: Measure -- scores 68% on the eval set, several fabricated details Step 5: Escalate -- add RAG grounding against the real policy documents -> re-measure -> 94% on the eval set, zero fabrications observed Step 6: Ship with a "was this helpful?" feedback button + human escalation path for anything the model flags as low-confidence
The eval set (built from the EXISTING chatbot's real historical queries, not synthetic ones) is what made the 68%→94% improvement measurable and honest, rather than a vague "it feels better now" — and the process only escalated to the more expensive RAG build once the cheaper prompting-only approach was proven insufficient against real success criteria, which is exactly right-sized engineering effort.
Daily-lifeWriting down what "done" looks like before starting a home renovation, rather than discovering the goalposts as you go.
ConsumerWhy a well-run product team A/B tests a new AI feature against a defined success metric rather than shipping based on a few impressive demo examples.
BusinessThe exact discipline that separates "we added AI" from "we measurably improved the customer experience" — a distinction stakeholders increasingly expect to see justified with real numbers.
EnterprisePrecisely the process a rigorous evolution of the Hero Electronics chatbot should follow: build the eval set from the real historical query log (you already have the data — 20% of queries the original bot couldn't handle), not from scratch.
Interview"How do you know a GenAI feature is actually ready to ship?" — it clears a pre-defined, representative evaluation set at an agreed bar, not "the demo looked good" — demos are notoriously unreliable indicators of real-world performance.

AI Economics — Cost, Latency & the Build/Buy Tradeoff C

A GenAI feature's real cost has multiple components: per-token API pricing (input and output priced differently), latency (user-perceived wait time, especially for long generations or agent loops with multiple tool calls), and the build/buy decision (using a hosted API vs. self-hosting an open-source model — self-hosting trades ongoing per-token cost for upfront infrastructure/ops cost and is rarely worth it below a significant volume threshold).

Worked example — hosted API vs. self-hosted breakeven
monthly_queries = 50,000 avg_cost_per_query_hosted_api = $0.004 monthly_cost_hosted = 50,000 * 0.004 = $200/month -- Self-hosting an open-source model: needs a dedicated GPU instance self_hosted_infra_cost = $1,500/month (a modest always-on GPU instance) -- Breakeven query volume where self-hosting starts being cheaper: breakeven = self_hosted_infra_cost / avg_cost_per_query_hosted_api = 1,500 / 0.004 = 375,000 queries/month
At 50,000 queries/month (roughly the scale implied by the chatbot's real query coverage numbers), the hosted API's $200/month is dramatically cheaper than a $1,500/month self-hosted GPU instance — self-hosting would only start making financial sense above ~375,000 queries/month, which is exactly the kind of concrete, computable threshold that should drive a real build-vs-buy decision rather than a general instinct that "self-hosting is more control, so it must be better."
Daily-lifeRenting a car for an occasional trip (hosted API, pay-per-use) versus buying and maintaining your own car (self-hosting, high fixed cost, only worth it above a usage threshold).
ConsumerWhy most consumer apps integrating GenAI features use a hosted API rather than running their own model infrastructure — the volume rarely justifies it.
BusinessA CFO-facing conversation about a GenAI feature should include real per-query cost, projected volume, and this breakeven math — not just "AI will make it better."
EnterpriseThe exact unit-economics conversation that should accompany any proposal to upgrade the Hero Electronics chatbot to an LLM-based architecture — is the query volume anywhere near the self-hosting breakeven, or is a hosted API clearly the right call.
Interview"When does self-hosting an open-source model make sense?" — very high query volume, strict data-residency/privacy requirements a hosted API can't satisfy, or a need for deep customization beyond what a hosted API's fine-tuning options allow — not simply "wanting more control" in the abstract.
Your CV"Bringing this build/buy cost lens to any GenAI proposal is exactly the kind of business-grounded technical judgment I'd want to demonstrate, tying straight back to owning the original chatbot's real cost-reduction numbers."

Alternative Approaches — Why This, Why Not That

GenAI systems involve a real stack of competing choices at every layer — the comparative reasoning that shows genuine engineering judgment.

Why prompt engineering before RAG or fine-tuning? It's free (no infrastructure), instant to iterate on, and a surprisingly large share of GenAI product problems are actually prompting/format problems, not knowledge or behavior problems — always try the cheapest lever first and prove it insufficient before building more infrastructure.

Why RAG over fine-tuning for most knowledge-grounding needs? RAG keeps the source of truth in an easily-updatable document store (change the policy document, the bot's answers update immediately, no retraining); fine-tuning bakes knowledge into frozen weights that go stale and require an expensive retrain to update — RAG wins whenever the underlying knowledge changes with any regularity, which is most real business knowledge.

Why a hosted API (OpenAI/Anthropic/Google) over a self-hosted open-source model (Llama/Mistral/Qwen)? Hosted APIs need zero infrastructure, get continuous model improvements for free, and are usually cheaper below a high volume threshold (see the AI Economics worked example); self-hosting wins on strict data-residency/privacy requirements, very high sustained volume, or a need for deep customization a hosted API's fine-tuning options don't support.

Why LangChain/LlamaIndex-style frameworks over hand-rolled orchestration code? Frameworks provide tested scaffolding for common patterns (RAG pipelines, agent loops, memory management) and faster initial development; hand-rolled code offers more control and fewer abstraction-layer surprises when debugging production issues — many experienced teams start with a framework for prototyping, then simplify to custom code for production once the pattern is proven, precisely because framework abstractions can obscure what's actually happening at the prompt level.

Why not just always use the largest, most capable model available? Bigger models cost more per token and add latency; a smaller, cheaper, faster model is often entirely sufficient for a well-scoped task (like classification or simple Q&A), reserving the largest models for genuinely complex reasoning — matching model size to task difficulty is a real cost/quality tradeoff, not a "bigger is strictly better" decision.

Red Flags — Never Say This

"GenAI and traditional ML are basically the same thing." Conflates discriminative and generative modeling — a fundamental category error that signals shallow understanding to any technical interviewer.
"RAG eliminates hallucination." RAG substantially reduces it by grounding in real retrieved text, but doesn't eliminate it — the model can still misread context or hallucinate when retrieval fails; overclaiming this is a well-known naive-practitioner tell.
"Fine-tuning is always better than RAG for adding knowledge." Backwards for most real cases — fine-tuning is expensive to keep current and RAG is almost always the right default for knowledge that changes; see the decision framework in this stage.
"More context is always better — just stuff everything into the prompt." Larger contexts cost more, add latency, and can actually degrade retrieval-relevant accuracy (models can get "lost in the middle" of very long contexts) — right-sized, well-chunked context beats maximalist context.
"An agent can just be given full autonomy and left to run without guardrails." Agents take real actions with real consequences — shipping one without scoped permissions, human-in-the-loop checkpoints, or monitoring is a genuine operational risk, not just a theoretical concern.
