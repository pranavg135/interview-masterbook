SQL Fundamentals

SELECT/WHERE/ORDER BY, DISTINCT, GROUP BY/HAVING, CASE WHEN, NULL handling, aggregations, string and date functions — the vocabulary everything else in this stage assumes.

SELECT, WHERE, ORDER BY A

Filter rows with WHERE before any grouping happens; sort the final result with ORDER BY. WHERE cannot reference an aliased SELECT column, because filtering happens before the SELECT list is evaluated.

Worked example
SELECT name, region, signup_date FROM customers WHERE region = 'West' AND signup_date >= '2025-01-01' ORDER BY signup_date DESC LIMIT 5;
nameregionsignup_date
Priya ShahWest2025-08-14
Arjun MehtaWest2025-06-02
Returns West-region customers who signed up in 2025 or later, newest first.
AnalogyFiltering emails by "unread + this week" then sorting by sender.
BusinessPulling this quarter's West-region customer list for a stakeholder review.
Interview"Why can't WHERE use a column alias?" — WHERE executes before SELECT in logical query order.
Your CVExactly the kind of query behind pulling a client-specific slice for a bi-weekly Axtria review.

DISTINCT B

Removes duplicate rows from the result set, evaluated across all selected columns together, not one at a time.

Worked example
SELECT DISTINCT region FROM customers;
Returns each unique region once — useful for quickly checking what values actually exist in a column before writing filters against it.
AnalogyListing every unique country represented in your contacts, not every contact.
Interview"DISTINCT on two columns — does it dedupe each column separately?" — no, it dedupes the combination of both columns together.
Your CVChecking the distinct set of client industries before building a NanoCloud coverage-recommendation template.

GROUP BY & HAVING A

GROUP BY collapses rows into per-group summaries; aggregate functions (SUM, COUNT, AVG) operate within each group. HAVING filters after aggregation — WHERE can't do this because the aggregate doesn't exist yet when WHERE runs.

Worked example
SELECT region, COUNT(*) AS num_customers, AVG(amount) AS avg_order FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY region HAVING COUNT(*) > 50 ORDER BY avg_order DESC;
Regions with more than 50 orders, ranked by average order value — HAVING filters the groups themselves, not the raw rows.
AnalogyGrouping receipts by store, then only keeping stores with over 50 receipts.
Interview"WHERE vs HAVING?" — WHERE filters rows before grouping; HAVING filters groups after aggregation.
Your CVAggregating calls per rep with HAVING avg duration > X is exactly rep-efficiency modeling at Axtria.

CASE WHEN A

Inline conditional logic inside a SELECT — the SQL equivalent of if/elif/else, evaluated top to bottom, stopping at the first matching condition.

Worked example
SELECT customer_id, CASE WHEN amount >= 1000 THEN 'Enterprise' WHEN amount >= 200 THEN 'Mid-market' ELSE 'SMB' END AS deal_tier FROM orders;
Buckets every order into a tier label in one pass — no separate lookup table needed.
AnalogySorting mail into "urgent / normal / junk" bins based on a few quick rules.
Interview"How is CASE different from a JOIN to a lookup table?" — CASE is inline logic for a few rules; a lookup table is better for many values or values that change often.
Your CVBucketing reps into efficiency tiers is a direct analog to the rep-allocation logic at Axtria.

NULL Handling A

NULL means "unknown," not zero or empty string — any arithmetic or comparison touching a NULL returns NULL, not true or false, which is why = NULL never works and IS NULL is required.

Worked example
SELECT customer_id, COALESCE(region, 'Unknown') AS region_filled FROM customers WHERE region IS NULL;
COALESCE substitutes a default when a value is NULL — critical before aggregating or joining on a column that might have gaps.
AnalogyA survey question left blank isn't the same as answering "zero" — NULL is "unknown," not a value.
Interview"Does COUNT(*) count NULLs?" — yes. "Does COUNT(column) count NULLs?" — no, it skips them.
Your CVMissing region/tier data in raw NanoCloud client exports needed exactly this handling before being usable in a recommendation.

Aggregations A

COUNT, SUM, AVG, MIN, MAX — each collapses many rows into one number, and each ignores NULLs except COUNT(*).

Worked example
SELECT rep_id, COUNT(*) AS num_calls, AVG(duration_min) AS avg_duration, SUM(CASE WHEN outcome='Converted' THEN 1 ELSE 0 END) AS conversions FROM calls GROUP BY rep_id;
Conditional aggregation inside SUM — counts only the rows matching a condition, a pattern you'll use constantly.
Interview"How do you count rows matching a condition without a subquery?" — SUM(CASE WHEN … THEN 1 ELSE 0 END), exactly above.
Your CVRep efficiency and cost-per-call at Axtria are aggregation queries at their core.

String Functions B

UPPER/LOWER, TRIM, SUBSTRING, CONCAT, LIKE/ILIKE for pattern matching, LENGTH — used constantly for data cleaning before analysis.

Worked example
SELECT name, LOWER(TRIM(name)) AS clean_name FROM customers WHERE name LIKE '%Corp%';
Finds customers with "Corp" anywhere in the name and normalizes casing/whitespace — a common first pass before deduping.
Interview"% vs _ in LIKE?" — % matches any number of characters, _ matches exactly one.
Your CVCleaning client-name variants across NanoCloud's 15 clients before any aggregation is exactly this.

Date Functions A

DATE_TRUNC, EXTRACT, DATEDIFF (syntax varies by engine) — used to bucket by month/week, or compute durations between dates.

Worked example
SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue FROM orders GROUP BY 1 ORDER BY 1;
Monthly revenue rollup — the exact building block behind any trend chart or forecasting model's training data.
Interview"How do you get someone's tenure in months?" — DATE_TRUNC or EXTRACT-based difference between hire_date and today, divided appropriately.
Your CVBuilding the time series that fed the Axtria forecasting model starts with exactly this kind of date bucketing.

Joins

The single most-tested SQL topic. Click each to expand — definition, when to use it, a worked query with result, and the interview trap that goes with it.

INNER JOINOnly rows matching in both tables

Returns rows where the join condition matches in both tables — non-matching rows on either side are dropped entirely.

SELECT c.name, o.order_id, o.amount FROM customers c INNER JOIN orders o ON c.customer_id = o.customer_id;
Interview trapCustomers with zero orders vanish entirely — if you need them, this is the wrong join.
Your CVMatching calls to reps who both exist in the current roster — Axtria efficiency modeling.
LEFT JOINAll rows from the left table, matched or not

Keeps every row from the left table; unmatched right-side columns come back as NULL. The most common join in real analytics work, because you usually don't want to silently drop rows.

SELECT c.name, COUNT(o.order_id) AS num_orders FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id GROUP BY c.name;
Every customer appears, including those with zero orders (COUNT returns 0, not NULL, because COUNT ignores NULLs but still counts the group).
Interview trap"Find customers with NO orders" needs a LEFT JOIN + WHERE o.order_id IS NULL — a very common interview puzzle (see Problem #7 below).
Your CVFinding NanoCloud clients with zero recent recommendations approved uses exactly this pattern.
RIGHT JOINAll rows from the right table — rarely used in practice

Mirror image of LEFT JOIN — keeps every row from the right table. Almost always rewritable as a LEFT JOIN with the table order swapped, which is why most style guides prefer LEFT JOIN for readability/consistency.

SELECT c.name, o.order_id FROM orders o RIGHT JOIN customers c ON o.customer_id = c.customer_id;
Interview"When would you actually use RIGHT JOIN?" — almost never by choice; it's equivalent to swapping table order in a LEFT JOIN.
FULL OUTER JOINAll rows from both sides, matched or not

Keeps every row from both tables — unmatched rows on either side get NULLs on the other side's columns. Useful for reconciliation: "what's in A but not B, and vice versa."

SELECT COALESCE(c.customer_id, o.customer_id) AS id, c.name, o.order_id FROM customers c FULL OUTER JOIN orders o ON c.customer_id = o.customer_id;
Business exampleReconciling a CRM export against a billing system export to find records only in one side.
CROSS JOINEvery combination of rows — Cartesian product

Pairs every row in table A with every row in table B — no join condition. Deliberately used to generate all combinations (e.g. every product × every region), but an accidental cross join is one of the most common real-world SQL bugs — usually from a forgotten or wrong join condition.

SELECT r.region, p.product_name FROM (SELECT DISTINCT region FROM customers) r CROSS JOIN products p;
Generates every region × product combination — useful as a scaffold before LEFT JOINing actual sales data onto it, to reveal which combinations have zero sales.
Interview trapA join with no ON clause, or one that matches many-to-many, silently becomes a cross join and inflates row counts — a classic "why did my numbers explode" debugging question.
SELF JOINA table joined to itself — hierarchies, comparisons within the same table

Join a table to itself using aliases, typically to compare rows to other rows in the same table — manager/employee hierarchies, or finding pairs.

SELECT a.rep_name, b.rep_name, a.region FROM reps a JOIN reps b ON a.region = b.region AND a.rep_id < b.rep_id;
Every unique pair of reps sharing a region — the rep_id < rep_id condition avoids duplicate pairs and self-pairing.
Your CVComparing a rep's efficiency to peers in the same region/territory at Axtria is a natural self-join.
Join duplication / one-to-manyWhy row counts explode after a join

When one customer has many orders, joining customers to orders multiplies each customer row by their number of orders — any SUM/AVG computed before deduplicating will be wrong (e.g. double-counting a customer-level value across every one of their order rows).

-- WRONG: double-counts customer-level 'signup_bonus' once per order row SELECT SUM(c.signup_bonus) FROM customers c JOIN orders o ON c.customer_id=o.customer_id; -- RIGHT: aggregate orders first, then join once per customer SELECT c.customer_id, c.signup_bonus, agg.total_orders FROM customers c JOIN (SELECT customer_id, SUM(amount) AS total_orders FROM orders GROUP BY customer_id) agg ON c.customer_id = agg.customer_id;
Interview trap"My revenue total looks 3x too high" is almost always this exact bug — aggregate the many-side first, then join.

CTEs & Subqueries

Common Table Expressions (CTE) A

A named, temporary result set defined with WITH, readable top-to-bottom and reusable within the same query — the modern replacement for deeply nested subqueries.

Worked example
WITH monthly_revenue AS ( SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue FROM orders GROUP BY 1 ) SELECT month, revenue, revenue - LAG(revenue) OVER (ORDER BY month) AS mom_change FROM monthly_revenue;
Builds the monthly rollup once, then reuses it to compute month-over-month change — far more readable than nesting the same aggregation inside a subquery.
Interview"CTE vs subquery — any performance difference?" — logically equivalent in most modern engines (some materialize, some inline); the real win is readability and reusability within one query.

Subqueries B

A query nested inside another — in the SELECT list, FROM clause, or WHERE clause.

Worked example
SELECT name FROM customers WHERE customer_id IN ( SELECT customer_id FROM orders WHERE amount > 5000 );
Customers who have placed at least one order over $5,000.

Correlated Subqueries A

A subquery that references a column from the outer query — re-evaluated once per outer row, which can be slow on large tables if not written carefully.

Worked example
SELECT c.name, (SELECT MAX(o.order_date) FROM orders o WHERE o.customer_id = c.customer_id) AS last_order FROM customers c;
Each customer's most recent order date — the inner query runs once per customer row, referencing that row's customer_id.
Interview"Why might you rewrite this as a window function instead?" — a correlated subquery re-runs per row; MAX(order_date) OVER (PARTITION BY customer_id) computes it once, typically faster at scale.

Window Functions

The highest-value SQL topic for analytics interviews — ranking, offsets, running totals, and percentiles, all without collapsing rows the way GROUP BY does.

ROW_NUMBER, RANK, DENSE_RANKRanking rows within groups

ROW_NUMBER: unique sequential number, no ties. RANK: ties share a rank, next rank skips (1,1,3). DENSE_RANK: ties share a rank, next rank doesn't skip (1,1,2).

SELECT rep_name, region, total_revenue, ROW_NUMBER() OVER (PARTITION BY region ORDER BY total_revenue DESC) AS rn, RANK() OVER (PARTITION BY region ORDER BY total_revenue DESC) AS rnk, DENSE_RANK() OVER (PARTITION BY region ORDER BY total_revenue DESC) AS drnk FROM rep_revenue;
reprevenuernrnkdrnk
Meera500111
Karan500211
Divya420332
Two tied reps at 500: RANK gives both rank 1, next rep jumps to rank 3; DENSE_RANK gives both rank 1, next rep is rank 2.
Interview trap"Find the top rep per region" — use ROW_NUMBER()=1 per partition, not just ORDER BY + LIMIT, which only works globally, not per group.
Your CVIdentifying the top-~60 reps for allocation at Axtria is exactly a ranking-within-partition problem.
LAG & LEADComparing a row to the previous/next row

LAG looks backward, LEAD looks forward, within an ordered partition — without a self-join.

SELECT month, revenue, LAG(revenue, 1) OVER (ORDER BY month) AS prev_month, revenue - LAG(revenue, 1) OVER (ORDER BY month) AS mom_change FROM monthly_revenue;
Month-over-month change without a self-join — this is the standard pattern for any period-over-period comparison.
Your CVQuarter-over-quarter market-share strategy inputs at Axtria are exactly LAG-based comparisons.
FIRST_VALUE & LAST_VALUEFirst/last row's value within a window

Returns a specific column's value from the first or last row of the window frame — useful for "compare every row to the group's starting/ending value."

SELECT customer_id, order_date, amount, FIRST_VALUE(amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS first_order_amount FROM orders;
Every order row now also shows that customer's very first order amount, for comparison — e.g. "has this customer's spend grown since their first order?"
Interview trapLAST_VALUE needs an explicit frame clause (ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) or it silently only looks at rows up to the current one, giving wrong results.
Running Totals & Rolling AveragesCumulative and moving-window aggregation

SUM/AVG with an OVER clause and an explicit frame — running total accumulates from the start; a rolling average uses a fixed-size trailing window.

SELECT month, revenue, SUM(revenue) OVER (ORDER BY month ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total, AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS rolling_3mo_avg FROM monthly_revenue;
running_total accumulates every prior month; rolling_3mo_avg smooths out month-to-month noise using only the current and prior 2 months — the exact building block behind the forecasting model's trend features.
Your CVA rolling average is very plausibly one of the input features to the Axtria forecasting model — worth being ready to say so.
PercentilesNTILE, PERCENT_RANK, CUME_DIST

NTILE(n) splits rows into n roughly-equal buckets (e.g. NTILE(4) = quartiles); PERCENT_RANK/CUME_DIST give a row's relative position as a 0-1 fraction.

SELECT rep_name, total_revenue, NTILE(4) OVER (ORDER BY total_revenue DESC) AS revenue_quartile FROM rep_revenue;
Splits reps into 4 performance quartiles — quartile 1 is the top-performing group, directly useful for a tiered allocation decision.
Your CVTiering reps into quartiles before the ~60-rep allocation decision at Axtria is a direct NTILE use case.

Analytics Patterns

Cohort analysis, retention, churn, funnels, conditional aggregation/pivoting, and deduplication — the patterns that turn raw SQL into a business answer.

Cohort Analysis & Retention A

Group users by the period they joined (their "cohort"), then track a metric over time relative to that join date — reveals whether a business is fundamentally getting better at keeping customers, not just growing.

Worked example
WITH cohorts AS ( SELECT customer_id, DATE_TRUNC('month', signup_date) AS cohort_month FROM customers ), activity AS ( SELECT customer_id, DATE_TRUNC('month', order_date) AS active_month FROM orders ) SELECT c.cohort_month, DATE_PART('month', AGE(a.active_month, c.cohort_month)) AS months_since_signup, COUNT(DISTINCT a.customer_id) AS active_customers FROM cohorts c JOIN activity a ON c.customer_id = a.customer_id GROUP BY 1,2 ORDER BY 1,2;
A cohort-by-month-since-signup table — the raw data behind a classic retention curve/triangle.
Your CVClient retention/reengagement patterns at NanoCloud across the 15-client base are exactly a cohort-style question.

Churn A

The inverse of retention — typically defined as no activity within a defined window. The exact cutoff (30/60/90 days) is a business decision, not a fixed rule.

Worked example
SELECT customer_id FROM customers c WHERE NOT EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id AND o.order_date >= CURRENT_DATE - INTERVAL '90 days' );
Customers with no order in the last 90 days — a working churn definition, ready to be refined by business input.

Funnel Analysis A

Counting users through sequential stages, and the drop-off between each — usually built with conditional aggregation across stage-flag columns.

Worked example
SELECT COUNT(DISTINCT customer_id) AS total_customers, COUNT(DISTINCT CASE WHEN stage >= 'contacted' THEN customer_id END) AS contacted, COUNT(DISTINCT CASE WHEN stage >= 'demo' THEN customer_id END) AS demo, COUNT(DISTINCT CASE WHEN stage >= 'closed' THEN customer_id END) AS closed FROM funnel_events;
One row showing the count at each funnel stage — drop-off rate at each step = 1 − (next_stage/prev_stage).
Your CVThe 80% query-coverage claim at Hero Electronics implies a funnel of query types handled vs. not — this pattern builds that view.

Conditional Aggregation & Pivot/Unpivot B

Turning long-format rows into wide-format columns using CASE inside aggregates (portable across engines) or native PIVOT (engine-specific).

Worked example
SELECT region, SUM(CASE WHEN category='Electronics' THEN amount ELSE 0 END) AS electronics_rev, SUM(CASE WHEN category='Apparel' THEN amount ELSE 0 END) AS apparel_rev FROM orders o JOIN order_items oi ON o.order_id=oi.order_id JOIN products p ON oi.product_id=p.product_id GROUP BY region;
One row per region, one column per category — a pivoted table built with plain, portable SQL.

Deduplication & Data Quality A

Removing duplicate rows using ROW_NUMBER() partitioned by the natural key, keeping only rn=1 — safer and more controllable than DISTINCT for row-level deduplication with tie-breaking logic.

Worked example
WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY signup_date DESC) AS rn FROM customers_raw ) SELECT * FROM ranked WHERE rn = 1;
Keeps exactly one row per customer_id — the most recent record — discarding older duplicates.
Your CVClient-name variants and duplicate records across NanoCloud's data exports are a real-world version of exactly this.

Execution Order, Query Plans & Performance

Logical Execution Order A

SQL is written FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY→LIMIT, but that's not the order it runs in.

Actual logical order
1. FROM / JOIN 2. WHERE 3. GROUP BY 4. HAVING 5. SELECT 6. ORDER BY 7. LIMIT
This is exactly why WHERE can't use a SELECT alias (step 2 runs before step 5), and why HAVING can reference an aggregate (step 4 runs after step 3).
InterviewAlmost every "why doesn't this query work" debugging question traces back to this exact ordering.

Query Plans & Indexes B

EXPLAIN shows how the database will actually execute a query — whether it uses an index (fast lookup) or a full table scan (checks every row). An index on a frequently-filtered/joined column can turn a full scan into a fast lookup.

Worked example
EXPLAIN SELECT * FROM orders WHERE customer_id = 4821; -- "Seq Scan on orders" (no index) vs "Index Scan using idx_customer_id" (indexed)
The indexed version reads a small number of rows via the index structure instead of scanning the entire table — the difference between milliseconds and minutes on a large table.
Interview trapIndexes speed up reads but slow down writes (every insert/update must also update the index) — not a free upgrade to add everywhere.

Partitioning & Large-Table Strategies C

Splitting a huge table (e.g. by date) so queries filtering on the partition key only scan the relevant slice, not the whole table — the same underlying idea behind Databricks' partitioning, covered again in Stage 5.

Your CVAny large-scale query against Axtria's full call/order history almost certainly benefits from date-based partitioning — worth naming even without deep DBA-level detail.

Red Flags

"SELECT * is fine, I'll just filter what I need in the app." — Wastes I/O and network bandwidth, and silently breaks if columns are added/reordered upstream. Select only needed columns in production code.
"I used a subquery in WHERE with = but there could be multiple rows." — Use IN or a correlated EXISTS, or the query throws a runtime error on more than one matching row.
"COUNT(column) and COUNT(*) are the same thing." — COUNT(*) counts all rows; COUNT(column) skips NULLs in that column. Easy to silently under-count.
"I joined and then summed — the total looked right so I moved on." — Classic join-duplication bug (see Joins section); "looks right" isn't the same as verified against a known total.
"GROUP BY just needs the columns I'm aggregating." — Every non-aggregated column in SELECT must appear in GROUP BY, or the query is ambiguous (and some engines silently pick an arbitrary row instead of erroring).
