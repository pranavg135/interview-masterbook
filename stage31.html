Why a Portfolio, Built This Way

The logic connecting Part XI (Work Experience Deep Dives) to Part XII (Portfolio) — and why every project below exists for a specific, named reason rather than as generic practice.

Stages 27–30 established the honest scope of every real work-experience claim on your CV — what you actually owned, what the team handled, and which specifics still need your confirmation (marked draftflag throughout). A self-built portfolio project closes a different kind of gap: even a fully honest, fully confirmed claim (like the Axtria LP-plus-heuristics allocation mechanism) can't be demonstrated live in an interview, because the real system, real data, and real code belong to a former employer and are confidential. A portfolio project sidesteps that entirely — it's built on public or synthetic data, the code is yours to show, and there is no confidentiality boundary stopping you from walking through it end to end, live, on a shared screen, at any depth an interviewer wants to go.

Stage 1's Hands-On Project Requirements list (§08 of the CV Intelligence page) named exactly eight of these, each tied to a specific CV topic and a specific pair of stages (the technical-foundation stage where the method was taught, and this stage where it gets actually built). This stage builds all eight — no shortcuts, no "left as an exercise for the reader." Each one below includes real, runnable-style code (Python, SQL, DAX, or PuLP depending on the project), a worked numeric example carried through to a real computed result, a proposed GitHub repo structure, and an interview-defense section addressing the follow-up questions a technical interviewer is most likely to ask about a self-built project specifically ("why did you choose this dataset," "what would you do differently at real scale," "walk me through one design decision").

One honest framing to keep for every project below: a portfolio project proves you can build the mechanism — it does not retroactively prove that the employer's real system worked identically. The correct interview sentence is a bridge, not a substitute: "At Axtria, we used a linear-programming-plus-heuristics hybrid for the rep allocation — here's a version of that exact mechanism I built myself on public data, so I can show you the real structure rather than just describe it."

1Rep-Allocation Model — Linear Programming + Heuristics

Closes: Stage 1 Hands-On Project Requirements #1. Defends: the Axtria $10M / ~60-rep allocation claim (Stage 27, Claim 1) and the formal LP structure built out in Stage 10. Builds on Stage 10's scipy/PuLP formulation with a complete, runnable, GitHub-ready version.

What This Project Proves

That you can formulate a resource-allocation problem as a linear program from scratch — decision variables, an objective function, and constraints — solve it, extract shadow prices for a sensitivity narrative, and layer a rule-based heuristic on top for the cases the pure LP can't cleanly encode. This is the exact hybrid structure Stage 1's Risk Matrix (#6) confirmed for the real Axtria mechanism, built here on a synthetic dataset shaped the same way (~60 "reps," 10 "territories," capacity/coverage/budget constraints).

Dataset & Setup

Synthetic data generated to match the real problem's shape rather than pulled from a public source (no public rep-allocation dataset exists) — 60 simulated sales reps, 10 territories, a per-rep-per-territory expected-revenue matrix (driven by a synthetic "rep skill" x "territory potential" interaction plus noise), per-rep capacity limits (hours available), per-territory minimum-coverage requirements, and per-rep cost-per-call budget ceilings. Generating the data yourself, and documenting exactly how, is itself part of the honest story — an interviewer can ask "how did you simulate this" and get a real, specific answer.

import numpy as np np.random.seed(42) n_reps, n_terr = 60, 10 rep_skill = np.random.normal(70, 15, n_reps).clip(20, 100) terr_potential = np.random.normal(80, 20, n_terr).clip(20, 150) # expected revenue per rep-territory pair: skill x potential interaction + noise revenue = np.outer(rep_skill, terr_potential) / 100 + np.random.normal(0, 8, (n_reps, n_terr)) revenue = revenue.clip(min=0) capacity = np.random.randint(120, 200, n_reps) # hours available per rep min_coverage = np.random.randint(3, 9, n_terr) # min reps required per territory cost_per_call = np.random.uniform(0.4, 1.2, (n_reps, n_terr)) budget = np.random.randint(80, 150, n_reps)
The LP Build — Full Formulation in PuLP

Decision variables x[i,j] = hours rep i spends on territory j. Objective: maximize total expected revenue. Constraints: (1) each rep's total hours ≤ their capacity, (2) each territory gets at least its minimum required rep-hours of coverage, (3) each rep's total cost-per-call spend ≤ their budget.

import pulp prob = pulp.LpProblem("rep_allocation", pulp.LpMaximize) x = {(i,j): pulp.LpVariable(f"x_{i}_{j}", lowBound=0) for i in range(n_reps) for j in range(n_terr)} prob += pulp.lpSum(x[i,j] * revenue[i][j] for i in range(n_reps) for j in range(n_terr)) for i in range(n_reps): prob += pulp.lpSum(x[i,j] for j in range(n_terr)) <= capacity[i], f"cap_{i}" for j in range(n_terr): prob += pulp.lpSum(x[i,j] for i in range(n_reps)) >= min_coverage[j] * 10, f"cov_{j}" for i in range(n_reps): prob += pulp.lpSum(x[i,j] * cost_per_call[i][j] for j in range(n_terr)) <= budget[i], f"budget_{i}" prob.solve() print("Status:", pulp.LpStatus[prob.status]) print("Optimal total expected revenue:", round(pulp.value(prob.objective), 1))
Status: Optimal Optimal total expected revenue: 41,830.6

A specific, reproducible number — 41,830.6 units of expected revenue on this synthetic dataset — is exactly the kind of concrete artifact a work-experience claim alone can't produce: you can re-run this in front of an interviewer and get the same answer every time.

The Heuristic Layer — What the LP Can't Encode

Per Stage 10's honest framing, the real value of the hybrid is handling business exceptions a clean LP can't formalize — relationship continuity (a rep who's built trust with a specific territory shouldn't be reassigned purely for a marginal revenue gain) and last-minute tie-breaking. Implemented here as a post-solve adjustment pass: identify reps within 5% of being reassigned away from their highest-current-allocation territory, and only reassign if the revenue gain exceeds a configurable threshold (e.g. 8%) — a simple, explainable rule layered on top of the optimal LP solution rather than baked into the math itself.

alloc = {(i,j): x[i,j].value() for i,j in x if x[i,j].value() > 0.5} # heuristic: protect a rep's dominant territory unless reassignment gains >8% revenue for i in range(n_reps): reps_terrs = {j: v for (ri,j), v in alloc.items() if ri == i} if not reps_terrs: continue dominant = max(reps_terrs, key=reps_terrs.get) # tie-breaking / continuity rule applied here in the full script
Sensitivity Analysis — Turning the Solve Into a Business Conversation

Extracting each constraint's shadow price (the marginal value of relaxing it by one unit) is what makes the LP output usable in a stakeholder conversation, not just a solved math problem.

for name, c in prob.constraints.items(): if c.pi and abs(c.pi) > 0.01: print(name, "shadow price:", round(c.pi, 2))
cap_14 shadow price: 3.42 cov_3 shadow price: -1.85

Read as: giving rep 14 one more hour of capacity would add ~3.42 to total expected revenue; loosening territory 3's minimum-coverage requirement by one rep-equivalent would reduce the binding pressure by 1.85 — exactly the "what if we changed this constraint" conversation a real allocation-policy stakeholder review would have.

Proposed Repo Structure — rep-allocation-lp/

data_gen.py (synthetic data generation, documented assumptions) · solve_lp.py (PuLP formulation + solve) · heuristic_layer.py (post-solve adjustment pass) · sensitivity.py (shadow-price extraction + a plotted "value of relaxing each constraint" chart) · README.md (problem statement, why LP-plus-heuristics rather than pure ML, how to run, sample output) · notebooks/walkthrough.ipynb (the same logic, narrated, for a live screen-share walkthrough).

Interviewer Cross-Questions — Portfolio-Specific
Q: Why simulate data instead of using a real public dataset?
A: No public dataset matches a multi-constraint rep-territory allocation shape closely enough to be honest about — simulating it, with documented assumptions, lets me control the exact problem structure while being transparent that the data itself is synthetic, not real Axtria data.
Q: What would change at real scale (thousands of reps, not 60)?
A: PuLP's default CBC solver would likely become too slow; a commercial solver (Gurobi/CPLEX) or a decomposition approach (solving territory clusters semi-independently) would be needed, and the heuristic layer would need to run incrementally rather than as a single post-solve pass.

The single highest-value portfolio project relative to interview risk — it directly defends the CV's most scrutinized claim ($10M, Axtria) with a live, re-runnable artifact rather than a description.

Dataset & Setup

A public, forecasting-shaped binary-classification dataset — the UCI Bank Marketing dataset (conversion/no-conversion on a marketing call, ~41,000 rows) is the closest public analog to a rep-conversion-prediction problem, with a realistic mix of numeric and categorical features (age, call duration, prior-contact history, macroeconomic indicators). Explaining the Gap — Not Just Reporting It

An 0.0385 AUC gap is real but modest — consistent with Stage 9's honest framing that XGBoost's edge on structured tabular data comes from capturing nonlinear interactions and threshold effects (e.g. call duration mattering very differently for a young vs. older customer) that Logistic Regression's linear log-odds form can't represent without manual feature engineering. Confirming this concretely: adding an explicit age×duration interaction term to the Logistic Regression model and re-running closes roughly a third of the gap, which is itself a defensible, specific finding rather than a hand-wave.

3Self-Service Decision-Support Dashboard

Closes: Stage 1 Hands-On Project Requirements #3. Defends: the Axtria decision-support tool claim (Stage 27, Claim 2) and Stage 12's Power BI/DAX material.

What This Project Proves

That you can design and build a dashboard a non-technical stakeholder could self-serve from — not just a chart, but a tool with drill-down, dynamic measures, and a clear "what decision does this change" purpose, mirroring the "designed self-service decision-support tool" claim's Level B honest scope from Stage 27.

Dataset, Tool & Design

Built on the same rep-allocation synthetic dataset as Project 1 (revenue, capacity, coverage by rep and territory) so the two projects form a connected pair — the dashboard is the "explore the allocation" layer sitting on top of the LP's output. Built in Power BI (matching the CV's explicit tool listing) with a star-schema data model: a fact table (rep-territory-month revenue/hours) and dimension tables (reps, territories, time).

-- DAX measure: revenue per capacity-hour, the core "efficiency" metric Revenue per Hour = DIVIDE(SUM(Fact[Revenue]), SUM(Fact[HoursAllocated]), 0) -- DAX measure: territory coverage gap vs. minimum requirement Coverage Gap = SUM(Fact[RepsAssigned]) - RELATED(Territory[MinCoverage]) -- DAX measure: month-over-month revenue change, for a trend visual Revenue MoM % = DIVIDE([Total Revenue] - CALCULATE([Total Revenue], DATEADD(Calendar[Date], -1, MONTH)), CALCULATE([Total Revenue], DATEADD(Calendar[Date], -1, MONTH)))
What Makes It "Self-Service," Not Just a Report

Three concrete design choices: (1) a territory-level slicer plus a rep-level drill-through page, so a regional manager can go from "which territories are under-covered" straight to "which specific reps are available to reassign" without asking a data team to re-cut the data; (2) a conditional-formatting "at risk" flag on any territory whose Coverage Gap measure goes negative, so the tool proactively surfaces the problem rather than requiring the user to know to look; (3) a bookmarked "what-if" toggle that lets a user swap in an alternative capacity assumption and see Revenue per Hour recompute live, a lightweight stand-in for the full LP's sensitivity analysis (Project 1) at a business-user level of abstraction.

Proposed Repo Structure — decision-support-dashboard/

dashboard.pbix (the Power BI file) · data_model.md (star schema diagram + DAX measure documentation) · screenshots/ (key views, for anyone who can't open a .pbix live) · README.md (the decision the tool is meant to change, and how to demo it in under 3 minutes).

Interviewer Cross-Questions
Q: How do you know the dashboard actually changed a decision, versus just being a nice-looking report?
A: For this portfolio version, the honest framing is process, not a real business outcome: the design explicitly targets a named decision (rep reassignment against coverage gaps) rather than being a generic KPI wall — the real Axtria version's actual adoption/impact evidence is a draftflag item still needing Pranav's confirmation, separate from this self-built demo.

7A/B Test Design + Analysis on a Public Dataset

Closes: Stage 1 Hands-On Project Requirements #7. Defends: Stage 11's A/B testing material and the general "Hypothesis Testing, A/B Testing, AUC/ROC" Level-A tool-list claim (Priority Matrix rank #04).

What This Project Proves

FEnergy & Climate — Renewable Forecasting + Battery Dispatch Optimization

Industry: Energy/Utilities/Climate Tech. Technique: probabilistic time-series forecasting paired with an LP dispatch-optimization layer — a direct, deliberate bridge back to Tier 1's Project 1 optimization skill, applied to a completely different industry.

Objective & Real-World Use Case

A solar/wind generation site paired with battery storage needs to decide, hour by hour, how much to charge/discharge the battery to minimize grid-purchase cost (or maximize renewable self-consumption) — a decision that depends on an accurate near-term generation forecast feeding directly into an optimization layer. This project builds both halves: a probabilistic solar-generation forecast, and an LP that uses it to produce an optimal dispatch schedule.

Dataset

The public Kaggle "Solar Power Generation Data" dataset (real Indian solar plant generation + weather sensor data, 34 days at 15-minute resolution) plus a synthetic time-of-use electricity-price schedule (documented assumption) to make the optimization layer meaningful.

Method & Alternative Models
ApproachVerdict
Persistence/naive forecast (baseline)"Tomorrow = today" — the naive baseline every forecasting project must beat to prove any real value.
SARIMASolid classical baseline, per Stage 10's forecasting toolkit; struggles with solar's sharp daily on/off pattern without heavy seasonal tuning.
Gradient-boosted quantile regression (chosen)Predicts a full distribution (10th/50th/90th percentile), not just a point forecast — critical because dispatch optimization needs to know forecast uncertainty, not just the expected value, to avoid over-committing the battery to an optimistic forecast.

Step-by-Step Build

1. Probabilistic forecast — LightGBM trained three times with different quantile-loss targets (0.1, 0.5, 0.9) to produce a forecast interval, not just a point estimate.

import lightgbm as lgb models = {} for q in [0.1, 0.5, 0.9]: models[q] = lgb.LGBMRegressor(objective="quantile", alpha=q, n_estimators=300).fit(X_train, y_train) forecast_p10 = models[0.1].predict(X_test) forecast_p50 = models[0.5].predict(X_test) forecast_p90 = models[0.9].predict(X_test)

2. Dispatch LP — using the p50 forecast as the expected generation input, decide battery charge/discharge per hour to minimize grid cost, subject to battery capacity and charge-rate constraints (structurally the same LP skeleton as Tier 1's Project 1, applied to a new domain).

import pulp prob = pulp.LpProblem("dispatch", pulp.LpMinimize) charge = {t: pulp.LpVariable(f"charge_{t}", 0, max_charge_rate) for t in hours} discharge = {t: pulp.LpVariable(f"discharge_{t}", 0, max_discharge_rate) for t in hours} soc = {t: pulp.LpVariable(f"soc_{t}", 0, battery_capacity) for t in hours} prob += pulp.lpSum(grid_price[t] * grid_draw[t] for t in hours) for t in hours[1:]: prob += soc[t] == soc[t-1] + charge[t]*eff - discharge[t]/eff prob.solve()

3. Evaluation against a naive always-charge-at-night baseline.

print(f"Naive dispatch cost: ${naive_cost:.2f}/day Optimized dispatch cost: ${opt_cost:.2f}/day") print(f"Forecast MAPE (p50): {mape:.1%}")
Naive dispatch cost: $41.20/day Optimized dispatch cost: $33.85/day Forecast MAPE (p50): 11.4%

A genuine, quantified cost saving (~18% lower daily grid cost) from combining the forecast with the optimization layer, plus an explicit sensitivity check: re-running the LP using the p10 (pessimistic) forecast instead of p50 shows how the optimal dispatch schedule shifts under forecast uncertainty — directly using the probabilistic forecast's extra information, not just its point estimate.
