03

Spark Architecture & Execution Model

How a PySpark program actually runs across a cluster — this is what separates "I've used the DataFrame API" from "I understand Spark."

Driver, Executors & Cluster Manager A

The driver runs your main program, builds the logical/physical plan, and schedules work. Executors (on worker nodes) run the actual tasks and hold data partitions in memory/disk. The cluster manager (YARN, Kubernetes, or Databricks' own) allocates the executors' resources.

Worked example
from pyspark.sql import SparkSession spark = SparkSession.builder.appName("RepAllocation").getOrCreate() # Driver builds the plan; when .collect() or .write() runs, # it ships tasks to executors, each working on a data partition df = spark.read.parquet("calls.parquet") # lazy — no data read yet print(df.rdd.getNumPartitions()) # e.g. 8 — one task per partition per stage
Nothing actually executes until an action (like .collect() or .write()) is called — reading the file only registers a lazy plan.
Daily-lifeDriver = project manager who plans the work; executors = the team members actually doing tasks in parallel.
ConsumerNetflix's recommendation batch jobs run this same driver/executor split across thousands of machines.
BusinessA retailer computing nightly inventory-reorder points across 10,000 SKUs × 500 stores in one Spark job instead of one machine looping sequentially.
EnterpriseAxtria's Databricks cluster splits the rep/call dataset across executors so allocation math runs in minutes, not hours.
Interview"What happens if a worker node dies mid-job?" — Spark recomputes the lost partition's lineage on another executor (fault tolerance via RDD lineage).
Your CVYou ran Databricks notebooks against a job cluster — you observed this driver/executor split directly in the Spark UI.

Lazy Evaluation: Transformations vs. Actions A

Transformations (select, filter, groupBy, join, withColumn) build a logical plan but don't execute. Actions (collect, count, show, write) trigger actual execution of the whole accumulated plan.

Worked example
calls = spark.read.parquet("calls.parquet") high_value = calls.filter(calls.call_value > 500) # transformation — lazy by_rep = high_value.groupBy("rep_id").count() # transformation — still lazy by_rep.show() # ACTION — now everything runs
Spark's Catalyst optimizer sees the whole chain (filter → groupBy → count) before executing, and can reorder/combine steps for efficiency — impossible if each line ran eagerly.
Daily-lifeWriting a full recipe before cooking anything, so you can reorder steps for efficiency, vs. cooking each line the moment you read it.
ConsumerA spreadsheet formula chain that only recalculates when you actually view the result cell.
BusinessChaining five filters on a sales dataset costs nothing until you actually ask for the count — lets you build complex pipelines cheaply.
EnterpriseDatabricks notebooks routinely chain 10+ transformations before one .write() — the whole thing optimizes as one plan.
Interview"Why does .show() sometimes rerun a slow computation that ran seconds ago?" — every action re-triggers the plan unless the result was cached with .cache()/.persist().
CV-specificExplains why your allocation notebook's early cells felt instant and the final .write() step took minutes — that's where actual execution happened.

Jobs, Stages & Tasks (the DAG) B

An action triggers a Job. Spark breaks the job into Stages at shuffle boundaries (where data must move between partitions, e.g. a groupBy or join). Each stage runs as parallel Tasks, one per partition.

Worked example
# calls.filter(...).groupBy("rep_id").agg(sum("call_value")) # Stage 1: read + filter (no shuffle needed, runs per-partition) # --- SHUFFLE BOUNDARY (groupBy needs same-key rows together) --- # Stage 2: aggregate per rep_id group, output
The Spark UI's DAG visualization shows exactly this: 2 stages, split at the groupBy, because that's where data has to be reshuffled across the network.
Daily-lifeSorting mail by zip code (no coordination needed) vs. tallying votes across all ballot boxes (everything has to come together first) — the second needs a "shuffle."
ConsumerA "trending hashtags" computation needs all mentions of the same tag gathered together — a shuffle stage.
BusinessRevenue-by-region needs every region's rows brought together before summing — that boundary is a new stage.
EnterpriseAxtria's rep-level rollups (call counts, revenue) hit a shuffle at the groupBy("rep_id") step — the visibly slower stage in the Spark UI.
Interview"Why is my join slow?" — often because it triggers a full shuffle; the fix is a broadcast join if one side is small (below).
Your CVYou've seen this directly: notebook cells with a groupBy visibly take longer in the Spark UI's job timeline than pure filter/select cells.

RDD vs. DataFrame vs. Dataset B

RDD: low-level, no schema, full control, no Catalyst optimization. DataFrame: schema-aware, SQL-like API, optimized by Catalyst — the default choice for almost everything today. Dataset: typed DataFrame (Scala/Java only, not available in PySpark the same way).

Worked example
# RDD — manual, no optimizer help rdd = sc.textFile("calls.csv").map(lambda l: l.split(",")) high_value_rdd = rdd.filter(lambda r: float(r[3]) > 500) # DataFrame — same logic, Catalyst-optimized, far faster in practice df = spark.read.csv("calls.csv", header=True, inferSchema=True) high_value_df = df.filter(df.call_value > 500)
The DataFrame version typically runs 2-5x faster on the same data because Catalyst can push the filter down, choose better join strategies, and skip unnecessary columns — the RDD version is a black box to the optimizer.
Daily-lifeRDD is like raw handwritten notes; DataFrame is a structured spreadsheet with named, typed columns the software itself can reason about.
ConsumerAlmost no modern Spark job at any company still uses raw RDDs directly — DataFrame is the default in production code everywhere.
BusinessA finance team's revenue pipeline written as a DataFrame lets analysts read/audit the transformation logic — an RDD's map/lambda chain is much harder to review.
EnterpriseAxtria's pipelines are entirely DataFrame-based — this is the API you actually used.
Interview"When would you ever drop to RDDs?" — rare: custom partitioning logic, or operations with no DataFrame equivalent (increasingly uncommon since Spark 3.x).
CV-specificYou can say honestly: "All my PySpark work was DataFrame-API level — I understand RDDs are the underlying abstraction but didn't need to drop to that level."
04

Core PySpark: Transformations, Joins & UDFs

The DataFrame operations you'll actually be asked to write live-coding, plus the join/UDF traps that separate people who've really used Spark from people who've only read about it.

select / filter / withColumn / groupBy / agg A

The core transformation vocabulary — nearly identical in spirit to Pandas/SQL, but every operation returns a new immutable DataFrame (Spark DataFrames, like RDDs, are immutable).

Worked example
from pyspark.sql import functions as F result = (calls .filter(F.col("call_value") > 0) .withColumn("is_high_value", F.when(F.col("call_value") > 500, 1).otherwise(0)) .groupBy("rep_id") .agg( F.sum("call_value").alias("total_value"), F.avg("call_value").alias("avg_value"), F.sum("is_high_value").alias("high_value_calls") ) .orderBy(F.desc("total_value")) ) result.show(3) # +------+-----------+---------+-----------------+ # |rep_id|total_value|avg_value|high_value_calls | # +------+-----------+---------+-----------------+ # | R014| 48210.5| 412.3 | 58 | # | R027| 45990.0| 398.1 | 52 |
Chained, immutable transformations — each step returns a new DataFrame reference; nothing mutates in place, which is what makes the whole chain safely parallelizable and re-computable on failure.
Daily-lifeLike a factory assembly line — each station (filter, then tag, then group) hands off an unchanged-upstream, transformed-downstream product.
ConsumerSpotify's "top artists this month" is exactly this groupBy + agg + orderBy pattern at massive scale.
BusinessComputing each rep's total call value and high-value-call count for a monthly performance review.
EnterpriseThis is close to the literal shape of code you wrote for Axtria's rep performance rollups feeding the allocation model.
Interview"Why F.col('x') instead of df.x or df['x']?" — F.col() is unambiguous and works even when column names collide across joined DataFrames.
Your CVDirect, defensible hands-on: "I wrote transformation chains like this for the rep-level feature aggregation feeding our allocation model."

Joins & Shuffle A

A Spark join between two large DataFrames requires a shuffle — rows with matching keys must land on the same executor. This is the single most common source of slow Spark jobs.

Worked example
reps_df = spark.read.parquet("reps.parquet") # ~60 rows — tiny calls_df = spark.read.parquet("calls.parquet") # millions of rows joined = calls_df.join(reps_df, on="rep_id", how="left") # Spark's optimizer auto-detects reps_df is small enough # (below spark.sql.autoBroadcastJoinThreshold, default 10MB) # and broadcasts it instead of shuffling the large side
Without broadcast, joining a 10M-row calls table to a 60-row reps table would still shuffle both sides across the network — wasteful when one side fits easily in each executor's memory.
Daily-lifeMatching every student to their teacher: if there are only 20 teachers, hand every classroom a copy of the teacher list rather than shuffling students to a central sorting point.
ConsumerAn e-commerce site joining millions of orders to a small product-category lookup table — broadcast join territory.
BusinessJoining a huge transactions table to a small store-metadata table for regional revenue rollups.
EnterpriseAxtria's calls-to-reps join (millions of calls to ~60 reps) is a textbook broadcast join — exactly your scale.
Interview"Your join is taking 20 minutes — what do you check first?" — Spark UI: is it shuffling both large sides, or did the broadcast threshold fail to trigger (e.g. because the "small" side wasn't actually that small)?
CV-specificYou can honestly describe having relied on Spark's automatic broadcast-join optimization for exactly this rep/call join shape.

Broadcast Joins (explicit) B

You can force a broadcast join with F.broadcast() when the optimizer's automatic threshold doesn't catch a case you know is safe to broadcast.

Worked example
from pyspark.sql.functions import broadcast joined = calls_df.join(broadcast(reps_df), on="rep_id", how="left") # Forces reps_df to be sent whole to every executor — # skips the shuffle entirely for this join
Explicit broadcast avoids relying on Spark guessing correctly from statistics that can be stale (e.g. after heavy filtering upstream) — a common production gotcha.
Daily-lifeHanding every team member a printed copy of a short reference sheet instead of making them all queue at one shared copy.
ConsumerA currency-conversion lookup (a handful of rates) broadcast-joined against millions of transactions.
BusinessJoining a small "region → target quota" table against a large sales-by-rep table.
EnterpriseA safe, defensible optimization to describe applying if the automatic threshold ever misfired on a filtered reps subset.
Interview"When would explicit broadcast hurt you?" — if the "small" table isn't actually small, you can blow out executor memory trying to broadcast it everywhere.
Your CVGood LEVEL B answer: "I understand and would use explicit broadcast() if I saw a join underperforming despite a small lookup table — didn't need to override the default in my own work."

UDFs vs. Built-in Functions A

Built-in pyspark.sql.functions run inside the JVM and are Catalyst-optimized. Python UDFs serialize data out to a Python process row-by-row — much slower. Always prefer built-ins; use UDFs only when there's truly no built-in equivalent.

Worked example
# SLOW — Python UDF, row-by-row serialization overhead from pyspark.sql.types import StringType from pyspark.sql.functions import udf def tier(value): return "high" if value > 500 else "low" tier_udf = udf(tier, StringType()) calls_df.withColumn("tier", tier_udf(calls_df.call_value)) # FAST — built-in, stays inside the JVM, Catalyst-optimized calls_df.withColumn("tier", F.when(F.col("call_value") > 500, "high").otherwise("low"))
The built-in version can be 2-10x faster on large data because it avoids serializing every row out to a Python worker process and back — a classic Spark interview trap question.
Daily-lifeA translator relaying every sentence between two people one at a time (UDF) vs. both people simply speaking the same language directly (built-in function).
ConsumerAny "why is my Spark job slow" post-mortem on Stack Overflow eventually finds a hidden UDF doing what a built-in could.
BusinessA custom "tier" classification originally written as a UDF, rewritten with F.when/.otherwise for a measurable speedup.
EnterpriseA realistic, honest Axtria answer: tier/threshold logic like this was written with built-ins, not custom UDFs, once the team learned the performance difference.
Interview"Are Pandas UDFs (vectorized UDFs) different?" — yes, they use Arrow to batch-process instead of row-by-row, much faster than plain UDFs but still slower than pure built-ins.
CV-specificA great "shows depth" answer even at Level B/C: explaining *why* built-ins beat UDFs, not just that they do.
05

Performance & Production Considerations

Partitioning, caching, and skew — the topics that separate "knows the DataFrame API" from "has actually run this in production."

Partitioning: repartition() vs. coalesce() B

repartition(n) does a full shuffle to redistribute data into exactly n partitions (can increase or decrease). coalesce(n) only merges existing partitions without a full shuffle — cheaper, but can only decrease partition count and may leave data unevenly sized.

Worked example
df = spark.read.parquet("calls.parquet") # 200 partitions from source files print(df.rdd.getNumPartitions()) # 200 # Before writing out a smaller result, reduce partitions cheaply: small_result = df.filter(F.col("region") == "West") small_result.coalesce(4).write.parquet("west_calls/") # vs. small_result.repartition(4) — same output count, # but repartition shuffles everything; coalesce just merges
coalesce(4) after a heavy filter avoids writing out 200 tiny files for a now-small dataset, without paying for a full shuffle repartition() would trigger.
Daily-lifeMerging four half-empty moving boxes into two full ones (coalesce) vs. dumping everything on the floor and re-packing from scratch into an exact new box count (repartition).
ConsumerAny data lake job avoiding the "small files problem" (millions of tiny output files) uses coalesce before writing.
BusinessA daily regional-subset export job using coalesce to avoid needless shuffle cost on an already-filtered, small result.
EnterpriseA realistic, honest thing to have observed: Databricks notebooks writing many small output files until someone added a coalesce() before the write.
Interview"Why not always use coalesce since it's cheaper?" — it can't rebalance skewed partitions or increase partition count; sometimes you genuinely need repartition's full shuffle.
CV-specificGood Level B/C answer even without deep personal tuning experience: explain the trade-off correctly and why it matters at your data's scale.

Caching & Persistence B

.cache() (memory only) or .persist(StorageLevel) (memory, disk, or both) tells Spark to keep a DataFrame's computed result around instead of recomputing it from scratch every time it's referenced by a later action.

Worked example
filtered = calls_df.filter(F.col("call_value") > 0) filtered.cache() # mark for caching — still lazy! filtered.count() # ACTION — this is what actually materializes the cache # Now every subsequent action on `filtered` reuses cached data # instead of re-reading + re-filtering from the source file by_region = filtered.groupBy("region").count() by_rep = filtered.groupBy("rep_id").count()
Without caching, both by_region and by_rep would independently re-execute the read + filter from scratch — caching pays the cost once and reuses the result.
Daily-lifeDoing the grocery shopping once and keeping the bags in the kitchen, rather than re-driving to the store every time you need an ingredient.
ConsumerA dashboard that recomputes the same filtered dataset for five different charts caches it once instead of five times.
BusinessAn analysis notebook computing multiple summary tables off the same filtered call log caches that filtered DataFrame first.
EnterpriseA realistic pattern in an Axtria-style notebook: cache the cleaned/filtered rep-call base table once, then branch into several different aggregations from it.
Interview"When would caching hurt you?" — caching data you only use once wastes executor memory that could go to actual computation; also, cached data can evict under memory pressure and silently get recomputed anyway.
CV-specificDefensible even at Level B: "I used .cache() on intermediate DataFrames that fed multiple downstream aggregations, to avoid redundant recomputation."

Data Skew & Salting C

Skew happens when one key (e.g. one region or one rep) has vastly more rows than others, so one task/partition takes far longer than the rest — the job's total time is bottlenecked by its single slowest task. Salting (adding a random suffix to the skewed key, splitting it into sub-keys, then aggregating twice) is the classic fix.

Worked example (conceptual — Level C, not personally executed)
# Problem: rep_id "R001" has 40% of all calls — its groupBy task # runs far longer than every other rep's task # Salting: split the skewed key into N synthetic sub-keys salted = calls_df.withColumn("salt", (F.rand() * 10).cast("int")) salted = salted.withColumn("salted_key", F.concat(F.col("rep_id"), F.lit("_"), F.col("salt"))) # groupBy(salted_key) spreads R001's rows across 10 tasks, # then a second aggregation combines the 10 partial results
Skew wasn't a real problem at Axtria's data volumes (millions of rows across ~60 reasonably balanced reps) — this is genuinely Level C conceptual knowledge, and it's fine to say so plainly.
Daily-lifeOne checkout line with a customer buying 500 items while nine other lines finish in seconds — the whole store's total wait time is bottlenecked by that one line.
ConsumerA "trending video" job where one viral video's comment count dwarfs every other video's — classic skew.
BusinessOne mega-account's transaction volume dwarfing every other client's in a groupBy-by-account job.
EnterpriseA LEVEL C honest answer: "I haven't hit real skew problems at Axtria's scale — reps were reasonably balanced — but I understand salting as the standard fix and would reach for it if one partition's task time visibly dominated the Spark UI's stage timeline."
Interview"How would you detect skew before it becomes a production problem?" — the Spark UI's task-duration distribution for a stage; one task taking 10x the median duration is the signature.
CV-specificSay plainly this wasn't your day-to-day scale — it reads as more credible than an inflated claim, and the conceptual answer above still shows real depth.

Databricks & Delta Lake

The managed platform layer — clusters, notebooks, jobs, and Delta Lake's ACID guarantees on top of plain Parquet, plus the medallion architecture pattern almost every Databricks shop uses.

Notebooks, Clusters & Cluster Types A

Databricks notebooks attach to a cluster — either an all-purpose cluster (interactive development, shared, billed while idle) or a job cluster (spun up for one scheduled job, terminated after, cheaper for production).

Worked example
# In a Databricks notebook cell: df = spark.read.table("bronze.calls") display(df.groupBy("rep_id").agg(F.sum("call_value").alias("total"))) # Interactive dev happens on an all-purpose cluster. # The same notebook, scheduled as a nightly Databricks Job, # runs on a fresh, disposable job cluster instead — # cheaper because it doesn't sit idle between runs
Job clusters are the cost-conscious default for anything scheduled and repeatable; all-purpose clusters are for active development and ad-hoc exploration.
Daily-lifeRenting a car for a one-day trip (job cluster) vs. keeping a car parked and ready outside your house all week (all-purpose cluster) — the second costs more even when unused.
ConsumerA photo-processing app spinning up cloud compute only when you hit "export," not continuously.
BusinessA nightly sales-rollup job runs on a job cluster; the analyst exploring the same data interactively that afternoon uses an all-purpose cluster.
EnterpriseDirect, honest CV claim: you built and scheduled pipelines in Databricks — this is literally that.
Interview"How do you control Databricks cost?" — job clusters over all-purpose for scheduled work, auto-termination on idle, right-sized worker counts.
Your CVA specific, checkable detail you can cite: "I scheduled our allocation refresh as a Databricks Job on a job cluster rather than leaving it on a shared interactive cluster."

Delta Lake: ACID Transactions & the Transaction Log A

Delta Lake adds a transaction log (_delta_log) on top of Parquet files, giving ACID guarantees, schema enforcement, and the ability to time-travel — none of which plain Parquet has on its own.

Worked example
df.write.format("delta").mode("overwrite").save("/delta/calls") # _delta_log/ now records every write as a versioned, atomic commit # Two jobs writing to the same Delta table concurrently: # Delta's optimistic concurrency control detects conflicts # and fails one write cleanly rather than silently corrupting data # — plain Parquet has no such protection
If two Databricks jobs tried to write the same plain-Parquet path simultaneously, you could get partial/corrupted files; Delta's transaction log prevents that by making each write atomic.
Daily-lifeA bank ledger where every transaction is logged in order and either fully applied or not at all — never half-applied.
ConsumerAny app where two people editing the same shared document simultaneously needs conflict handling, not silent overwrite.
BusinessA finance close process where two different jobs can't be allowed to corrupt the same ledger table if they overlap.
EnterpriseDirect Level A claim: you worked with Delta Lake tables specifically, including versioning — this is core to that.
Interview"What does Delta Lake add over plain Parquet?" — ACID transactions, schema enforcement/evolution, time travel, and unified batch+streaming reads.
Your CVSpecific and checkable: "Our rep allocation output table was a Delta table — versioned, so we could audit exactly what changed between allocation runs."

Time Travel & MERGE (Upsert) A

Delta's version history lets you query any prior state of a table (time travel). MERGE INTO lets you upsert — update matched rows, insert new ones — in a single atomic statement, instead of a fragile delete-then-insert.

Worked example
-- Time travel: see the allocation table as it looked yesterday SELECT * FROM allocations VERSION AS OF 12; SELECT * FROM allocations TIMESTAMP AS OF '2026-08-21'; -- MERGE: upsert this week's allocation updates MERGE INTO allocations AS target USING new_allocations AS source ON target.rep_id = source.rep_id WHEN MATCHED THEN UPDATE SET target.territory = source.territory, target.quota = source.quota WHEN NOT MATCHED THEN INSERT *;
MERGE handles both "rep already exists, update their numbers" and "brand-new rep, insert them" in one atomic statement — avoiding the race condition and partial-failure risk of a manual delete+insert.
Daily-lifeGit's version history — you can check out yesterday's state, or merge in a set of changes without wiping what wasn't touched.
ConsumerA note-taking app's "restore previous version" feature.
BusinessCorrecting a data error by rolling back to a known-good prior version of a reporting table.
EnterpriseDirect Level A claim: "I used MERGE to upsert weekly allocation refreshes without wiping the whole table, and time travel to audit what an allocation looked like before a correction."
Interview"How would you debug 'the allocation numbers changed unexpectedly'?" — time travel to the prior version, diff it against the current version to see exactly what changed and when.
Your CVOne of your strongest, most specific, fully honest technical claims — lean into it.

Medallion Architecture: Bronze → Silver → Gold B

A layered pattern: Bronze = raw ingested data, untransformed. Silver = cleaned, deduplicated, joined, validated. Gold = business-level aggregates ready for reporting/modeling.

Worked example
# Bronze: raw call logs exactly as ingested from the source system bronze_calls = spark.read.format("delta").load("/bronze/calls") # Silver: cleaned — dedup, null-handling, joined to rep dimension silver_calls = (bronze_calls .dropDuplicates(["call_id"]) .filter(F.col("call_value").isNotNull()) .join(broadcast(reps_df), "rep_id")) silver_calls.write.format("delta").save("/silver/calls") # Gold: business-ready aggregate for the allocation model gold_rep_summary = silver_calls.groupBy("rep_id").agg( F.sum("call_value").alias("total_value")) gold_rep_summary.write.format("delta").save("/gold/rep_summary")
Each layer is a Delta table in its own right — this lets teams reprocess Silver from Bronze if cleaning logic changes, without re-ingesting from the source system.
Daily-lifeRaw grocery ingredients (bronze) → washed and chopped, ready to cook (silver) → the finished, plated meal (gold).
ConsumerRaw app clickstream logs → cleaned sessionized events → a "daily active users" dashboard metric.
BusinessRaw POS transactions → validated, deduplicated sales records → a gold "revenue by region by day" table feeding the BI dashboard.
EnterpriseA very plausible, honest Axtria pattern: raw call/order feeds (bronze) → cleaned, rep-joined records (silver) → the allocation-ready rep summary table (gold) you personally built transformation logic for.
Interview"Why not just clean everything in one step?" — layering makes debugging and reprocessing far cheaper: a cleaning-logic bug only requires rebuilding Silver+Gold from Bronze, not re-ingesting from source.
CV-specificEven without the exact "bronze/silver/gold" vocabulary having been used at Axtria, the underlying pattern (raw → cleaned → aggregated) is very likely what you actually built — honest to frame it that way.

Databricks Jobs / Workflows (Orchestration) A

Databricks Workflows let you schedule notebooks/scripts as jobs, chain multi-task pipelines with dependencies, set retries, and get failure alerts — the production scheduling layer.

Worked example
# Conceptual job DAG (defined via UI or a job JSON spec): # Task 1: ingest_calls (runs nightly at 2am) # Task 2: clean_and_join (depends on Task 1 succeeding) # Task 3: build_gold_summary (depends on Task 2) # Task 4: run_allocation_model (depends on Task 3) # retries: 2, alert on failure: yes
If Task 2 fails, Task 3 and 4 don't run at all, and the team gets an alert — vs. a naive single-script approach where a mid-pipeline failure can leave downstream tables in an inconsistent state.
Daily-lifeA recipe where you can't start baking until the dough has risen — later steps depend on earlier ones finishing correctly.
ConsumerA photo backup app that only starts uploading edited photos after the raw upload step finishes successfully.
BusinessA finance close pipeline where "generate report" can't run until "reconcile ledger" has succeeded.
EnterpriseDirect Level A claim: "I built and scheduled our allocation refresh pipeline as a multi-task Databricks Job with dependencies between the ingest, clean, and model-run steps."
Interview"How do you handle a failed nightly job?" — Databricks Job retries + alerting, plus checking which task failed via the run's task graph rather than re-running the whole pipeline blindly.
Your CVTies directly to "built/scheduled pipelines in Databricks" — this is exactly that claim, made concrete.

Unity Catalog & Governance C

Unity Catalog is Databricks' centralized governance layer — table/column-level access control, data lineage, and a unified metastore across workspaces. Worth knowing conceptually even without hands-on admin experience.

Worked example (conceptual)
-- Three-level namespace under Unity Catalog: -- catalog.schema.table SELECT * FROM axtria_prod.sales.rep_allocations; -- Governance: grant read access to an analyst role GRANT SELECT ON axtria_prod.sales.rep_allocations TO `analytics_team`;
This is Level C — good to be able to explain the concept and why it matters (governance, lineage, one metastore instead of siloed per-workspace permissions) without overclaiming personal admin ownership.

Red Flags — Never Say This

"Spark is just faster Pandas." Wrong framing — Spark's advantage is distributed computation across a cluster; on a single machine with data that fits in memory, Pandas is often faster due to Spark's overhead.
"I optimized Spark jobs at massive scale." Not true for you — your scale was moderate batch (millions of rows), and an interviewer's specific follow-up (skew, cluster sizing at that scale) will expose an inflated claim immediately.
"UDFs and built-in functions perform the same." They don't — UDFs (especially plain Python ones) serialize data out of the JVM and are meaningfully slower; this is one of the most common Spark interview trap questions.
"Delta Lake is just Parquet with a different name." Wrong — the transaction log is what gives it ACID guarantees, time travel, and schema enforcement; plain Parquet has none of that.
Confusing transformations and actions. Saying "the filter ran immediately" when nothing runs until an action is called signals a shallow, first-week understanding of Spark's lazy execution model.
